## A. 数据模型与流水线

### A1. 三张邮件表的最终字段

- **已定**：待审表由出站与入站**共用一张**并加 `direction` 字段；审查不通过的记录**移入独立的 rejected 表**（因此物理表数量由最初说的 2 张变为 3 张）；**不支持附件**。
- **未定**：待审表与邮件表的具体字段清单；`message_id` / `in_reply_to` / `references` 的存储与唯一性约束；线程关联字段（回复指向哪封原始出站邮件）的命名与语义。
- **为什么没定**：预研阶段只确认方向，细节留到需求阶段。
- **阻塞**：Alembic 首次迁移、SQLAlchemy 模型、所有仓储层代码。

### A2. rejected 表保留什么、是否对外可查

- **未定**：rejected 表是否保留邮件完整原文（还是只存 id + 原因 + 时间）；拒审原因是否通过 `GET /v1/messages/{id}` 暴露给调用方（返回 `status=rejected` + 原因）。
- **为什么没定**：预研阶段只确认方向，细节留到需求阶段（该问题曾被提出，所有者回答「还没有到这一步」）。
- **阻塞**：拒审路径的可观测性设计；若不保留原文，误判将无法复核、无法补发。

### A3. 审查通过后，待审行是否物理删除

- **当前设计倾向**：单个事务内删除待审行 + 写入目标表（邮件表或 rejected 表）。
- **未定**：是否需要保留待审行的历史（例如只标记状态不删除），以便完整追溯链路。
- **阻塞**：待审表的清理策略与增长控制。

### A4. IMAP 游标与幂等键的设计

- **已定（机制）**：两部分都要，不能只靠其一——
  1. **游标**：必须记录 `UIDVALIDITY` + 已处理的最大 UID，否则 10 秒一次的轮询会反复全量重扫；**游标管效率**。
  2. **幂等唯一键**：必须有独立于游标的唯一键（**邮箱 + `UIDVALIDITY` + `UID`**），用于保证不重复入库；**唯一键管正确性**。
- **未定（形态）**：独立 `imap_cursors` 表，还是通用 KV 表（`key` / `value` / `updated_at`）；是否需要支持多邮箱。**留到需求阶段或写首个迁移时决定。**
- **既有实现的事实与教训**（旧服务的做法，新服务不沿用）：
  - 每次 `search ALL` 取最后 N 封（**全量重扫**，没有游标）；
  - `.eml` 以 `Message-ID` 命名，**同名即覆盖**；
  - `index.json` 每次重建，且**只保留最新一批**——这是**数据丢失策略**，与已定的「孤儿也入库、不丢数据」（见 A5）直接冲突，**新服务不沿用**。
- **必须记住的教训**：**`Message-ID` 不能作为幂等键**。RFC 5322 中它不是必需字段，且存在被重复使用的情况；用它做去重键或文件名会**静默覆盖、丢数据**。幂等键必须是「邮箱 + `UIDVALIDITY` + `UID`」。
- **阻塞**：入站拉取流的幂等实现（机制已定，仅形态待定）。

### A5. 关联不上的入站邮件如何标识

- **已定**：关联不上的邮件（非回复、或 `References` / `In-Reply-To` 缺失）**标记为孤儿但仍然入库，不丢数据**。这一点在与所有者确认「单专用邮箱 + IMAP UID 游标 + `References` 关联」方案时一并确认。
- **未定**：孤儿邮件的状态取值如何命名；是否需要以及如何在查询接口中区分「正常回复」与「孤儿邮件」。
- **阻塞**：邮件表状态枚举与回复查询接口的响应契约。

## B. 邮件收发与路由

### B1. 发件人与回复路由策略（**核心行为已定**，剩余部分不阻塞预研阶段）

- **已定**（见 ADR-0012）：
  - `From` **固定取服务配置**（`MAIL_FROM_ADDRESS`），**不允许调用方传入**；
  - 服务端**显式写入 `Reply-To`**，值等于 IMAP 拉取所用的信箱（`REPLY_TO_ADDRESS`）。
- **未定**（留需求阶段）：
  1. `REPLY_TO_ADDRESS` 与 IMAP 账号**一致性的保证方式**——启动即失败 / 启动告警 / 仅人工保证；
  2. **IMAP 登录名不是邮箱地址时的映射方式**。
- **不再阻塞预研阶段**：核心行为（`From` 固定 + 显式 `Reply-To`）已经锁定，上述两点属于配置校验与映射细节，可以在需求阶段决定。**原「高优先级阻塞」标记已撤销。**
- **背景纠正**：此前「回复能否回来完全取决于是否强制 `Reply-To`」的说法**不准确**——按 RFC 5322，有 `Reply-To` 则回复发往它，否则发往 `From`；既有实现的 `From` 恰好就是 IMAP 拉取的信箱，回路本来就是通的。显式写 `Reply-To` 是**加固**，不是「让回路能通」的前提。详见 ADR-0012。

### B2. SMTP 与 IMAP 的真实参数

- **未定**：SMTP 主机 / 端口 / 是否 STARTTLS / 发件账号与密码；IMAP 主机 / 端口 / 专用回复邮箱地址 / 目标邮箱文件夹。
- **当前状态**：全部收敛到 `.env`，仓库只提供 `.env.example` 占位值。
- **阻塞**：真实环境联调（本地开发用 Mailpit / 容器化邮件捕获可先替代）。

### B3. 发信失败的重试与终态

- **已定**：重试 3 次，退避间隔 **15s / 30s / 60s**。
- **未定**：SMTP 返回码的分类策略（永久性错误是否直接置 `failed` 而不重试）；达到重试上限后是否需要通知调用方。
- **阻塞**：状态机实现与写库字段（`attempt_count` / `next_attempt_at` / `last_error`）。

### D7. 服务器 Docker 的版本与 image store 模式（已基本核实，不再是高优先级）

- **已核实**（服务器实测原文照录）：**Client 26.1.3 / Server Engine 26.1.3 / API 1.45（最低 1.24）/ containerd 1.6.32 / runc 1.1.12 / linux/amd64 / 构建于 2024-05-16**。
- **结论**：
  - **Engine ≥ 25 满足** → 可以读 OCI 归档。
  - **`--platform` 不可用**：API 为 **1.45 < 1.48**，因此 `docker save` / `docker load` 的 `--platform` 参数**不可用**——这是**由 API 版本直接推出的结论，不是推测**。
  - **剩余唯一未确认项：image store 模式**。Engine 26 默认是 classic，但**此处不作断言**。判断命令：`docker info` 看 Storage Driver——`overlay2` = classic，`overlayfs` = containerd store。它决定归档能否被加载。
  - **缓解手段**：只交付**单平台 amd64 归档** + 交付前做归档自检（做法见 `deploy/` 下的文档）。
- **保留的风险**：Docker 官方**已不再支持 CentOS 8 作为宿主**，服务器上这版 Docker（构建于 2024-05-16）处于**无官方支持状态**。
- **已降级**：交付链的关键未知项已收敛为「一个可用一条命令确认的模式问题」，因此撤销「高优先级阻塞」标记。

### D8. 服务器侧 Docker 是否有可升级路径

## E. 依赖与工具选型

### E1. IMAP 客户端选型

- **候选**：
  - `imapclient` 4.1.0：**官方 CI 矩阵明确包含 3.14**，但是**同步库**，在 asyncio 中需要放到线程池执行。
  - `aioimaplib` 2.0.1：原生异步，但**未声明支持 3.14**（classifier 只到 3.12、CI 只到 3.11），且自 2025-01 起已 20 个月未发新版。
- **未定**：选哪个。
- **阻塞**：入站拉取流实现。

### E2. `httpx` 的使用风险（性质已变化）

- **原事实**：`httpx` 0.28.1（2024-12 发布）的 classifier 只到 3.12，官方 issue #3644「Fix compatibility with Python 3.14」**仍然 open**，PR #3722 未合并；而 FastAPI 的 `TestClient` 依赖它。
- **本地实测观测（2026-09-29）**：在目标环境跑 `pytest` **通过（1 passed）**，但同时输出了一条弃用警告，完整文本为：

  ```
  StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead
  ```

  该警告来自 `.venv` 中的 `fastapi/testclient.py`。
- **结论已更新**：`httpx` 在 Python 3.13 上**实际可用**（我们的测试已经跑通），因此「能不能用」这一风险**已经关闭**；风险性质转变为「**将来会不会被 FastAPI / Starlette 弃用掉**」——上游已经在推进 `httpx2`。
- **待决（新）**：**是现在就跟进 `httpx2`，还是等 FastAPI 正式移除 `httpx` 支持时再迁移？**
  - 现在跟进：提前消除弃用风险，但 `httpx2` 的成熟度、与 `TestClient` 的配合情况尚需验证。
  - 等到被迫迁移：省下当前工作量，但迁移会与 FastAPI 的大版本升级耦合在一起，风险更集中。
  - 这属于**依赖替换**（`AGENTS.md` §6 的不可逆决策范畴），**必须由项目所有者决定，不由实现者代决**。
- **阻塞**：测试依赖的锁定方式；`pyproject.toml` 中 `httpx` / `httpx2` 的取舍。

### E3. 数据库驱动与迁移工具

## F. 安全与合规

### F1. 审查能力如何真正落地

- **已定**：一期做成**永远通过的空实现占位**（见 ADR-0009）。
- **未定**：后续采用本地规则（敏感词库 + 正则）还是本地病毒扫描（ClamAV/clamd），还是外部内容安全 API。
- **注意到的冲突**：生产服务器**完全离线**，因此「调用外部内容安全 API」与离线前提冲突；若采用本地病毒库，则**病毒库的离线更新机制**需要单独设计。
- **这是「生产完全离线」这条硬约束的直接后果**（见 ADR-0005 §8.5 与 AGENTS.md 的硬约束清单）：审查能力的选型不能只看检出率，还必须回答「离线环境下它如何更新、如何保持有效」。若最终只能选外部 API，那意味着「完全离线」这条约束本身需要重新评估。
- **阻塞**：审查供应商接口的最终形态与上线合规性。

### F2. 审查不通过时的通知方式

- **阻塞**：是否需要出站回调能力。

### F3. API 鉴权

- **已定**：一期**不做鉴权**，接口占位留空（预留鉴权依赖的位置）。
