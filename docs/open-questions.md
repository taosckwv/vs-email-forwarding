# 待决问题清单

本文件记录**尚未决策**的问题。每条说明：当前状态、为什么还没定、阻塞了什么。

处理约定：问题一旦被决定，应从本文件**移除**，并把结论沉淀为 ADR（不可逆决策）或 `specs/` 下的规格（特性细节）。不要在这里堆积已经定下来的事情。

> 已冻结的决策见 `adr/`。本文件只放「还没定」的。

## A. 数据模型与流水线

### A1. 三张邮件表的最终字段

- **已定**：待审表由出站与入站**共用一张**并加 `direction` 字段；审查不通过的记录**移入独立的 rejected 表**（因此物理表数量由最初说的 2 张变为 3 张）；**不支持附件**。
- **未定**：待审表与邮件表的具体字段清单；`message_id` / `in_reply_to` / `references` 的存储与唯一性约束；线程关联字段（回复指向哪封原始出站邮件）的命名与语义。
- **为什么没定**：项目所有者明确表示「还没有到需求阶段」。
- **阻塞**：Alembic 首次迁移、SQLAlchemy 模型、所有仓储层代码。

### A2. rejected 表保留什么、是否对外可查

- **未定**：rejected 表是否保留邮件完整原文（还是只存 id + 原因 + 时间）；拒审原因是否通过 `GET /v1/messages/{id}` 暴露给调用方（返回 `status=rejected` + 原因）。
- **为什么没定**：需求阶段未开始（该问题曾被提出，所有者回答「还没有到这一步」）。
- **阻塞**：拒审路径的可观测性设计；若不保留原文，误判将无法复核、无法补发。

### A3. 审查通过后，待审行是否物理删除

- **当前设计倾向**：单个事务内删除待审行 + 写入目标表（邮件表或 rejected 表）。
- **未定**：是否需要保留待审行的历史（例如只标记状态不删除），以便完整追溯链路。
- **阻塞**：待审表的清理策略与增长控制。

### A4. IMAP 游标（`sync_state`）的设计

- **已定**：必须有游标状态存储，否则 10 秒一次的拉取会把同一封回复重复入库。
- **未定**：是独立的 KV 表（`key` / `value` / `updated_at`），还是专用的 `imap_cursors` 表（邮箱、UID、时间）；是否需要支持多邮箱。
- **阻塞**：入站拉取流的幂等实现。

### A5. 关联不上的入站邮件如何标识

- **已定**：关联不上的邮件（非回复、或 `References` / `In-Reply-To` 缺失）**标记为孤儿但仍然入库，不丢数据**。这一点在与所有者确认「单专用邮箱 + IMAP UID 游标 + `References` 关联」方案时一并确认。
- **未定**：孤儿邮件的状态取值如何命名；是否需要以及如何在查询接口中区分「正常回复」与「孤儿邮件」。
- **阻塞**：邮件表状态枚举与回复查询接口的响应契约。

## B. 邮件收发与路由

### B1. 发件人与回复路由策略（**高优先级**）

- **未定**：`From` 是固定取服务配置，还是允许调用方传入；是否在服务端**强制**写入 `Reply-To` = 专用回复邮箱。
- **为什么关键**：内容形态已定只有纯文本/HTML，**没有抄送/密送，也没有自定义邮件头**，因此回复能否回到「可被 IMAP 拉取的信箱」完全取决于服务端是否强制 `Reply-To`。这条不决定，回复可能全部丢失。
- **为什么没定**：需求阶段未开始。
- **阻塞**：发信适配器实现、待审表与邮件表字段、端到端闭环验证。

### B2. SMTP 与 IMAP 的真实参数

- **未定**：SMTP 主机 / 端口 / 是否 STARTTLS / 发件账号与密码；IMAP 主机 / 端口 / 专用回复邮箱地址 / 目标邮箱文件夹。
- **当前状态**：全部收敛到 `.env`，仓库只提供 `.env.example` 占位值。
- **阻塞**：真实环境联调（本地开发用 Mailpit / 容器化邮件捕获可先替代）。

### B3. 发信失败的重试与终态

- **已定**：重试 3 次，退避间隔 **15s / 30s / 60s**。
- **未定**：SMTP 返回码的分类策略（永久性错误是否直接置 `failed` 而不重试）；达到重试上限后是否需要通知调用方。
- **阻塞**：状态机实现与写库字段（`attempt_count` / `next_attempt_at` / `last_error`）。

## D. 环境与部署

### D1. 基础镜像的 tag 与 digest（写进脚本前复核）

- **已定**：生产基础层锁定 **`python:3.13-slim-trixie`**（不用浮动的 `python:3.13-slim`，实测它一个月内即从 Debian 12 bookworm / glibc 2.36 漂到 Debian 13 trixie / glibc 2.41）；预演容器用 **`almalinux:8`**；构建阶段的 uv 基础镜像定为 **`ghcr.io/astral-sh/uv:0.12.20`**（已用 registry manifest 请求验证存在，digest `sha256:100047e7…`）。
- **已验证活跃**：`python:3.13-slim-trixie` 与 `python:3.13-slim` 当前是**同一个 digest**（amd64 `sha256:37134a49d21d2120e4c4d73bb76f8a4ab9aef31f096f7ec2ead48c2feead4332`）；`postgres:17`、`almalinux:8`、`axllent/mailpit:v1.31.3` 均确认存在且活跃。
- **待复核**（已由「未定」降级）：把上述 tag 写进 `Dockerfile` / `compose*.yaml` / `deploy/` 脚本**之前**逐一复核 digest 是否仍一致。浮动 tag 与 digest 都会随时间漂移，而本项目镜像靠 `save` / `load` 离线交付，这一步不能省。
- **当前不阻塞任何工作**：`Dockerfile` 可以照上述 tag 编写，只需在落笔时复核一次。

### D2. 部署脚本的具体形态

### D4. 数据库备份、日志采集与保留期

### D5. 邮件数据保留期与清理策略

- **未定**：邮件表、rejected 表、`sync_state` 是否需要定期归档或清理；保留多久；是否有合规要求的保留期限。
- **阻塞**：是否需要引入定期清理任务（会成为第五条流）。

### D6. 本地邮件捕获工具（Mailpit）是否采用

- **当前状态**：开发环境规划中包含 Mailpit（同时提供 SMTP 与 IMAP，用于在本地验证「发出去 → 被拉回来 → 关联上原邮件」的完整回路），但该选择在对话中**未获项目所有者明确确认**（相关提问被取消），目前属于待确认。
- **备选**：其他本地邮件捕获方案；或不做本地捕获、集成测试直接打真实邮件服务器（不推荐，会向真实邮箱发测试邮件且不可控）。
- **补充事实**：候选镜像 `axllent/mailpit:v1.31.3` 已确认存在且活跃；但**是否采用 Mailpit 本身仍未定**（上方待确认状态不变）。
- **阻塞**：`compose.dev.yaml` 的最终内容与集成测试方案。

### D7. 服务器 Docker 的版本与 image store 模式（**高优先级**）

- **未知**：服务器上 Docker 的 **Engine 版本、CLI 版本、以及 image store 模式**（classic 还是 containerd）。所有者只确认了「已装好、能正常用」，未提供版本号。
- **为什么阻塞**：这条**直接决定整条交付链能否成功**（详见 ADR-0006 §3）：
  - 需要 **Engine ≥ 25**（moby v25.0.0 起 `docker save` 产出 OCI 归档）；
  - 需要 **CLI ≥ 28**（`--platform` 参数自该版本起支持）；
  - **Docker Desktop 与 Engine ≥ 29 默认使用 containerd image store**，而 **classic image store 不支持 image index / manifest list**，会导致多平台镜像加载失败。
  - 另外，Docker 官方**已不再支持 CentOS 8 作为宿主**，服务器上这版 Docker 处于无官方支持状态。
- **如何解除**：在服务器上执行 `docker version` 并回报 Engine / CLI 版本与 image store 模式；若 Engine < 25 或 CLI < 28，需要先升级 Docker，否则 `save` / `load` 的格式可能与预期不符。
- **阻塞**：`deploy/` 脚本的最终形态、`--platform` 与镜像归档格式的选择、离线交付演练能否开始。

## E. 依赖与工具选型

### E1. IMAP 客户端选型

- **候选**：
  - `imapclient` 4.1.0：**官方 CI 矩阵明确包含 3.14**，但是**同步库**，在 asyncio 中需要放到线程池执行。
  - `aioimaplib` 2.0.1：原生异步，但**未声明支持 3.14**（classifier 只到 3.12、CI 只到 3.11），且自 2025-01 起已 20 个月未发新版。
- **未定**：选哪个。
- **阻塞**：入站拉取流实现。

### E2. `httpx` 的使用风险（性质已变化）

- **原事实**：`httpx` 0.28.1（2024-12 发布）的 classifier 只到 3.12，官方 issue #3644「Fix compatibility with Python 3.14」**仍然 open**，PR #3722 未合并；而 FastAPI 的 `TestClient` 依赖它。
- **本地实测观测（2026-09-29）**：在目标环境跑 `pytest` **通过（1 passed）**，但同时输出了一条弃用警告，完整文本为：

  ```
  StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead
  ```

  该警告来自 `.venv` 中的 `fastapi/testclient.py`。
- **结论已更新**：`httpx` 在 Python 3.13 上**实际可用**（我们的测试已经跑通），因此「能不能用」这一风险**已经关闭**；风险性质转变为「**将来会不会被 FastAPI / Starlette 弃用掉**」——上游已经在推进 `httpx2`。
- **待决（新）**：**是现在就跟进 `httpx2`，还是等 FastAPI 正式移除 `httpx` 支持时再迁移？**
  - 现在跟进：提前消除弃用风险，但 `httpx2` 的成熟度、与 `TestClient` 的配合情况尚需验证。
  - 等到被迫迁移：省下当前工作量，但迁移会与 FastAPI 的大版本升级耦合在一起，风险更集中。
  - 这属于**依赖替换**（`AGENTS.md` §6 的不可逆决策范畴），**必须由项目所有者决定，不由实现者代决**。
- **阻塞**：测试依赖的锁定方式；`pyproject.toml` 中 `httpx` / `httpx2` 的取舍。

### E3. 数据库驱动与迁移工具

- **未定**：`asyncpg` 还是 `psycopg3`（async）；SQLAlchemy 2.x 的 async 用法细节。
- **已定**：PostgreSQL + Alembic 作为迁移工具（见 ADR-0008）。
- **阻塞**：`pyproject.toml` 的运行时依赖清单与首次迁移。

### E4. 生产环境是否需要离线依赖包

- **已定**：服务器完全离线，交付物只有镜像 tar + 运行脚本，**服务器上不需要 Python 与 uv**。
- **未定**：是否额外交付一份离线 wheels / 离线 Python 运行时，以便在服务器宿主机上直接跑脚本或临时排障。
- **阻塞**：交付物清单的最终形态。

## F. 安全与合规

### F1. 审查能力如何真正落地

- **已定**：一期做成**永远通过的空实现占位**（见 ADR-0009）。
- **未定**：后续采用本地规则（敏感词库 + 正则）还是本地病毒扫描（ClamAV/clamd），还是外部内容安全 API。
- **注意到的冲突**：生产服务器**完全离线**，因此「调用外部内容安全 API」与离线前提冲突；若采用本地病毒库，则**病毒库的离线更新机制**需要单独设计。
- **这是「生产完全离线」这条硬约束的直接后果**（见 ADR-0005 §8.5 与 AGENTS.md 的硬约束清单）：审查能力的选型不能只看检出率，还必须回答「离线环境下它如何更新、如何保持有效」。若最终只能选外部 API，那意味着「完全离线」这条约束本身需要重新评估。
- **阻塞**：审查供应商接口的最终形态与上线合规性。

### F2. 审查不通过时的通知方式

- **未定**：调用方如何得知邮件被拒（仅靠 `GET /v1/messages/{id}` 主动轮询，还是需要回调/通知）。
- **阻塞**：是否需要出站回调能力。

### F3. API 鉴权

- **已定**：一期**不做鉴权**，接口占位留空（预留鉴权依赖的位置）。
- **未定**：何时补上、采用何种方式（API Key / mTLS / 内网白名单）。
- **风险**：内网服务一旦跨网段暴露即为未授权可用；需要与 C2 的端口暴露范围一并评估。
