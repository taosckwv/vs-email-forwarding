## A. 数据模型与流水线

### A1. 三张邮件表的最终字段

- **已定**：待审表由出站与入站**共用一张**并加 `direction` 字段；审查不通过的记录**移入独立的 rejected 表**（因此物理表数量由最初说的 2 张变为 3 张）；**不支持附件**。
- **未定**：待审表与邮件表的具体字段清单；`message_id` / `in_reply_to` / `references` 的存储与唯一性约束；线程关联字段（回复指向哪封原始出站邮件）的命名与语义。
- **为什么没定**：预研阶段只确认方向，细节留到需求阶段。
- **阻塞**：Alembic 首次迁移、SQLAlchemy 模型、所有仓储层代码。

### A2. rejected 表保留什么、是否对外可查

- **未定**：rejected 表是否保留邮件完整原文（还是只存 id + 原因 + 时间）；拒审原因是否通过 `GET /v1/messages/{id}` 暴露给调用方（返回 `status=rejected` + 原因）。
- **为什么没定**：预研阶段只确认方向，细节留到需求阶段（该问题曾被提出，所有者回答「还没有到这一步」）。
- **阻塞**：拒审路径的可观测性设计；若不保留原文，误判将无法复核、无法补发。

### A3. 审查通过后，待审行是否物理删除

- **当前设计倾向**：单个事务内删除待审行 + 写入目标表（邮件表或 rejected 表）。
- **未定**：是否需要保留待审行的历史（例如只标记状态不删除），以便完整追溯链路。
- **阻塞**：待审表的清理策略与增长控制。

### A4. IMAP 游标与幂等键的设计

- **已定（机制）**：两部分都要，不能只靠其一——
  1. **游标**：必须记录 `UIDVALIDITY` + 已处理的最大 UID，否则 10 秒一次的轮询会反复全量重扫；**游标管效率**。
  2. **幂等唯一键**：必须有独立于游标的唯一键（**邮箱 + `UIDVALIDITY` + `UID`**），用于保证不重复入库；**唯一键管正确性**。
- **未定（形态）**：独立 `imap_cursors` 表，还是通用 KV 表（`key` / `value` / `updated_at`）；是否需要支持多邮箱。**留到需求阶段或写首个迁移时决定。**
- **既有实现的事实与教训**（旧服务的做法，新服务不沿用）：
  - 每次 `search ALL` 取最后 N 封（**全量重扫**，没有游标）；
  - `.eml` 以 `Message-ID` 命名，**同名即覆盖**；
  - `index.json` 每次重建，且**只保留最新一批**——这是**数据丢失策略**，与已定的「孤儿也入库、不丢数据」（见 A5）直接冲突，**新服务不沿用**。
- **必须记住的教训**：**`Message-ID` 不能作为幂等键**。RFC 5322 中它不是必需字段，且存在被重复使用的情况；用它做去重键或文件名会**静默覆盖、丢数据**。幂等键必须是「邮箱 + `UIDVALIDITY` + `UID`」。
- **阻塞**：入站拉取流的幂等实现（机制已定，仅形态待定）。

### A5. 关联不上的入站邮件如何标识

- **已定**：关联不上的邮件（非回复、或 `References` / `In-Reply-To` 缺失）**标记为孤儿但仍然入库，不丢数据**。这一点在与所有者确认「单专用邮箱 + IMAP UID 游标 + `References` 关联」方案时一并确认。
- **未定**：孤儿邮件的状态取值如何命名；是否需要以及如何在查询接口中区分「正常回复」与「孤儿邮件」。
- **阻塞**：邮件表状态枚举与回复查询接口的响应契约。

## B. 邮件收发与路由

### B1. 发件人与回复路由策略（**核心行为已定**，剩余部分不阻塞预研阶段）

- **已定**（见 ADR-0012）：
  - `From` **固定取服务配置**（`MAIL_FROM_ADDRESS`），**不允许调用方传入**；
  - 服务端**显式写入 `Reply-To`**，值等于 IMAP 拉取所用的信箱（`REPLY_TO_ADDRESS`）。
- **未定**（留需求阶段）：
  1. `REPLY_TO_ADDRESS` 与 IMAP 账号**一致性的保证方式**——启动即失败 / 启动告警 / 仅人工保证；
  2. **IMAP 登录名不是邮箱地址时的映射方式**。
- **不再阻塞预研阶段**：核心行为（`From` 固定 + 显式 `Reply-To`）已经锁定，上述两点属于配置校验与映射细节，可以在需求阶段决定。**原「高优先级阻塞」标记已撤销。**
- **背景纠正**：此前「回复能否回来完全取决于是否强制 `Reply-To`」的说法**不准确**——按 RFC 5322，有 `Reply-To` 则回复发往它，否则发往 `From`；既有实现的 `From` 恰好就是 IMAP 拉取的信箱，回路本来就是通的。显式写 `Reply-To` 是**加固**，不是「让回路能通」的前提。详见 ADR-0012。

### B2. SMTP 与 IMAP 的真实参数

- **已定**：SMTP / IMAP 的**账号与密码由所有者提供**。
- **已定（只定了处理方式）**：**证书信任随账号一并确认**——若使用私有 CA，届时需要把根证书带入宿主 / 镜像。至于实际是否为私有 CA、根证书如何带入，**要等拿到账号后才能确定**，现在不预设。
- **未定**：SMTP 主机 / 端口 / 是否 STARTTLS；IMAP 主机 / 端口 / 专用回复邮箱地址 / 目标邮箱文件夹；以及证书信任的具体内容（是否私有 CA、根证书的带入方式）。
- **当前状态**：全部收敛到 `.env`，仓库只提供 `.env.example` 占位值。
- **阻塞**：真实环境联调（本地开发用 Mailpit / 容器化邮件捕获可先替代）。

### B3. 发信失败的重试与终态

- **已定**：重试 3 次，退避间隔 **15s / 30s / 60s**。
- **未定**：SMTP 返回码的分类策略（永久性错误是否直接置 `failed` 而不重试）；达到重试上限后是否需要通知调用方。
- **阻塞**：状态机实现与写库字段（`attempt_count` / `next_attempt_at` / `last_error`）。

### D3. 开发机的 Docker 能力（**已查清：本机装不了 Docker Desktop**）

- **已定**：开发与集成测试用容器化 PostgreSQL 与邮件捕获服务；本机 Python 用 uv 跑快速检查。
- **实测事实（已查清，比原先的判断更严重）**：
  - 开发机是 **Windows 10 专业版 22H2（Build 19045）**，但它**本身是一台虚拟机**：`Manufacturer=SANGFOR`、`Model=Standard PC (i440FX + PIIX, 1996)`、`HypervisorPresent=True`。
  - **未暴露嵌套虚拟化**：`VirtualizationFirmwareEnabled=False`、`SecondLevelAddressTranslationExtensions=False`、`VMMonitorModeExtensions=False`（CPU 被掩码为 `Intel Core 2 Duo T7700`）。
  - **WSL2 与 Hyper-V 都未安装**：`wsl --status` 退出码 50、无 `lxss` 目录、无 `vmcompute.exe` / `vmms.exe` 服务。
- **结论（对原判断的修正）**：
  - 原文写的是「本机尚未安装 Docker（需管理员权限、WSL2、可能重启）」，**不准确**。准确表述是：**Docker Desktop 的两个后端（WSL2 / Hyper-V）都依赖硬件虚拟化与 SLAT / EPT，而本机是未暴露嵌套虚拟化的虚拟机，因此两个后端在本机都不可用**。这不是「装一下就行」，而是「**这台机器装不了**」。
  - 另注：当前工作会话**不是管理员**、且**审批提示已关闭**，因此**无法提权执行安装**（即使装得上有意义，本机也跑不起来）。
- **关键澄清（决定了替代路径）**：**Linux 上的 Docker 不需要硬件虚拟化**（容器只用内核 namespaces / cgroups），所以上述限制**只卡 Windows 上的 Docker Desktop**——只要有一台 **Linux 机器或 Linux 虚拟机（不需要嵌套虚拟化）**，就能跑镜像构建与部署预演。**这正是「把构建放到 Linux 侧（本仓库现定为生产服务器，见下方已定项）可行」的依据。**
- **已定（原「剩余待定」已由所有者拍板，见 ADR-0013）**：**构建环境放在生产服务器上**——镜像**在 CentOS 8 生产服务器上本地构建**，基础镜像以镜像 tar 形式从外部带入并 `docker load`。因此原先「在生产服务器上自建，还是单独一台 Linux 构建机」**已不再是未定项**。
  - **注意**：这**不**改变上面的实测事实，也不改变「Linux 上的 Docker 不需要硬件虚拟化」这一澄清——开发机本身仍是 Windows 虚拟机，**仍然装不了 Docker Desktop**；变的只是「构建放在哪」这个决策。
- **另有一条实现细节未定（与「构建环境放在哪」无关，见 ADR-0013）**：基础镜像 tar **由哪台机器、用什么工具产出**——**未定**，本次不展开。
- **阻塞**：**开发机侧**的集成测试、容器化开发环境、部署预演仍跑不了（本机装不了 Docker Desktop 这一点未变）；构建与部署则改在生产服务器上进行（见 ADR-0013）。

### D7. 服务器 Docker 的版本与 image store 模式（**已确认 / 关闭**）

- **已确认**（服务器实测原文照录）：

  - **image store 模式**：`docker info` 显示 **`Storage Driver=overlay2`** ⇒ **classic image store**（classic 模式显示 `overlay2`，**只有 containerd 模式才显示 `overlayfs`**；这与仓库既有的判断口径一致）。

  - **Engine ≥ 25 满足** → 可以读 OCI 归档。

  - **宿主可用工具**：`rsync` / `tar` / `sha256sum` / `python3` / `curl` / `wget` / `unzip` **都有**；**没有 `git`**。
  - **安装介质**：`sr0` 7.7G iso9660 挂载在 `/run/media/root/CentOS-8-2-2004-x86_64-dvd`（**CentOS 8.2 安装 DVD ISO**）。
  - **时区与时钟**：**所有者告知服务器时间已同步，无需再关注**（见 **D10**，已确认 / 关闭）。早期诊断曾输出 `Time zone: America/New_York (EDT, -0400)`、`System clock synchronized: no`，**该输出已过期，不要再据此断言「时钟未同步」或「时区为纽约」**。
- **影响与结论**：
  - **SELinux 为 `Enforcing`** ⇒ 容器 bind mount **必须**处理 `:z` / `:Z`（或等价的安全上下文策略），否则挂载卷的读写会被拒绝。这条已从「**未确认**」变为「**必须做**」。
  - **firewalld 为 `active` 且 iptables 是 `nf_tables` 后端** ⇒ 端口暴露与容器转发的规则需要规划（与 C2 一并评估）。**已知踩点**：**firewalld reload 会冲掉 Docker 插入的 iptables 链，可能导致容器网络中断**——部署脚本与运维文档须避免在容器运行期间 reload。
  - **有 `rsync`、没有 `git`** ⇒ 源码上传走 **rsync / 归档**即可，**不依赖 git**。
  - **`sr0` 挂着 CentOS 8.2 安装 DVD ISO** ⇒ 可以配成**本地 repo**，用 `BaseOS` / `AppStream` 安装与宿主 8.2 **版本完全匹配**的包（例如 `git`、`chrony`），且**不需要公网**。这条**修正**此前「宿主完全装不了包」的说法。（**注意**：**D11 已确认内网 yum 源可用**（含 vault / EPEL 8 等 30+ 仓库），因此宿主装包不止 DVD 一条路；但**必须留意宿主 yum 源版本与 8.2 发行版不匹配的风险，见 D12**。DVD 源仍是确定可用的兜底。）
  - **磁盘**：`/` 可用 **46G**，另有独立的 **256G ext4 盘挂在 `/data`** ⇒ **磁盘不是约束**；**建议** PostgreSQL 数据落在 **`/data`**（见下方待确认）。Swap 7.9G。
  - **资源**：**8 vCPU / 7.6 GiB 内存 / 7.9 GiB swap** ⇒ **所有者已确认这就是最终生产规格**（此前「2 vCPU / 2 GB 是否够用」的疑问**就此消除**，不再是待确认项）；与 F1 直接相关：**内存约束已彻底解除**（详见 F1）。
- **待确认**：
  - 是否真的配置并长期保留**本地 DVD repo**，以及 ISO / 挂载点在重启后是否仍然可用；具体要离线安装哪些包。
  - **PostgreSQL 数据目录是否落在 `/data`**（磁盘布局允许，但这属于部署形态，**待所有者确认**）。

### D10. 生产服务器的时钟（**已确认 / 关闭**）

- **已确认**：**所有者明确表示服务器时间同步正常，无需再关注。**
- 因此本条**不再追踪**以下内容（此前曾被列为待确认，现全部作废，**不要再去核对**）：`CST` 缩写的歧义、`System clock synchronized` 的当前状态、`chronyd` 是否 `active` / `enabled`、同步源是什么、是否监控时钟偏移。
- **保留一条不随本条关闭的既有约定**：应用时间一律使用**带时区的 `datetime`、按 UTC 存储**（`AGENTS.md` §7），显示层再转换。这与服务器时区取什么值无关，**不构成新决策**。
- **仅供将来排查时参考（不是待办）**：时钟漂移会同时影响三处——TLS 证书有效期校验、邮件 `Date` 头、以及重试退避调度（`next_attempt_at`，见 B3）。若日后出现「TLS 握手失败」或「该重试的邮件长时间不动」这类症状，可把时钟作为排查方向之一，但**现在不需要任何动作**。

### D11. 生产环境「内部镜像源」的存在与覆盖范围（**已确认 / 关闭**）

- **已确认**（所有者告知 + 生产环境实测，结论见 ADR-0013）：生产环境的真实形态是「**与公网隔离，但可达内网镜像源**」（Nexus 类，以路径形式暴露）。因此文档中一直沿用的「**生产完全离线**」表述**不成立**，已按 ADR-0013 更正为「**与公网隔离，但可达内网镜像源；运行时不得依赖任何外部网络**」。
- **三类覆盖的实测结论**（本条目只记结论与证据类型，**不含任何地址 / 主机名 / 端口 / 账号**）：
  1. **yum / RPM 源：可用**。`makecache` 成功，**实际安装过包**；覆盖 CentOS vault、EPEL 8、Rocky 9、Alma 9 等 **30+ 仓库**。
  2. **PyPI 源：可用且覆盖完整**。代理公共 PyPI，**真实安装过 wheel 成功** ⇒ **构建时能装 wheel**（与 E4 直接相关，见 E4）。
  3. **Docker 镜像内容：镜像内容完整，但 Docker 客户端当前无法直连消费**。源里多个官方镜像的 **manifest 可访问**，但该源以路径形式暴露、**没有独立端点**，与 Docker registry 协议要求不符，直连报 **content-type 解析错误**。**该问题尚未解决，登记为已知限制，本次不要求解决。**
- **所有者据此已做的两个决策（见 ADR-0013）**：
  1. **交付形态改为在 CentOS 8 生产服务器上本地构建镜像**（不再由开发机构建）；
  2. **基础镜像的进入方式：从外部机器导出为镜像 tar 再带入服务器**（`docker load`）。「外部机器」具体是哪一台、用哪种工具产出 tar，属**实现细节，本次未定**。
- **对原推论的影响**：本条目原写「若覆盖则现有交付形态可能不再必要」——该推论**已由所有者拍板落地**（交付形态确已变更），结论沉淀在 **ADR-0013**。**本条目不再作为待确认项。**
- **仍然成立的部分**：Docker 镜像内容**不可被客户端直连消费** ⇒ **基础镜像仍必须由外部以 tar 形式带入**；D7 关于「本地镜像为空 / 基础镜像必须离线带入」的结论，在新的带入方式下**依然有效**。
- **不写进仓库的内容**：**不得**记录任何内网地址、主机名、IP、端口、账号（`AGENTS.md` §8.4 / §10）；仓库内只允许占位符（如 `<internal-nexus-host>`）。

### D12. 宿主 yum 源版本与发行版不匹配的风险（**待确认**）

- **风险事实**：宿主**当前配置的 yum 源是 CentOS 8.5 的 vault**，而宿主发行版实测为 **CentOS 8.2.2004**（见 D9）。从 **8.5 源**安装宿主包时，**可能顺带把部分系统包乃至内核升到 8.5**——在这台**已 EOL** 的生产机上，这属于**未授权的局部升级**（所有者尚未授权任何系统版本升级）。
- **两条可选规避方向（本条目不替所有者选择）**：
  1. **指向与宿主版本匹配的源**：改用 8.2 对应的 vault 仓库，使安装到的包与宿主发行版一致；
  2. **使用已挂载的安装 DVD ISO**：`sr0` 上的 CentOS 8.2 安装 DVD（见 D9）配成本地 repo，包版本与宿主 **8.2 完全匹配**，且不需要公网。
- **为什么没定**：是否改动宿主的软件来源属于运维决策，**由所有者决定**；预研阶段只登记风险与可选方向。
- **不阻塞**：本身不阻塞当前工作，但**在服务器上安装任何宿主包之前必须先看本条**。

### D 节硬约束提醒：内网源地址等敏感信息只允许落在被忽略的本地配置

> **本节不是待确认项，而是硬约束提醒**（依据 `AGENTS.md` §8.4 / §10）。

- 内网源地址、主机名、IP、端口、账号、凭据**只能**落在 **`.env`**（已被 gitignore）或**其它被忽略的本地配置**中。
- **仓库内只允许占位符**（如 `<internal-nexus-host>`），包括文档、脚本、注释与示例输出。
- 这类配置项的**示例形态应体现在 `.env.example` 的占位符上**（`.env.example` 由根配置维护，本文件不改动它）。
- 后果与既有红线一致：真实值一旦进入仓库或提交历史，等同泄露内网拓扑与凭据。

## E. 依赖与工具选型

### E1. IMAP 客户端选型

- **候选**：
  - `imapclient` 4.1.0：**官方 CI 矩阵明确包含 3.14**，但是**同步库**，在 asyncio 中需要放到线程池执行。
  - `aioimaplib` 2.0.1：原生异步，但**未声明支持 3.14**（classifier 只到 3.12、CI 只到 3.11），且自 2025-01 起已 20 个月未发新版。
- **未定**：选哪个。
- **阻塞**：入站拉取流实现。

### E2. `httpx` 的使用风险（性质已变化）

- **原事实**：`httpx` 0.28.1（2024-12 发布）的 classifier 只到 3.12，官方 issue #3644「Fix compatibility with Python 3.14」**仍然 open**，PR #3722 未合并；而 FastAPI 的 `TestClient` 依赖它。
- **本地实测观测（2026-09-29）**：在目标环境跑 `pytest` **通过（1 passed）**，但同时输出了一条弃用警告，完整文本为：

  ```
  StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead
  ```

  该警告来自 `.venv` 中的 `fastapi/testclient.py`。
- **结论已更新**：`httpx` 在 Python 3.13 上**实际可用**（我们的测试已经跑通），因此「能不能用」这一风险**已经关闭**；风险性质转变为「**将来会不会被 FastAPI / Starlette 弃用掉**」——上游已经在推进 `httpx2`。
- **待决（新）**：**是现在就跟进 `httpx2`，还是等 FastAPI 正式移除 `httpx` 支持时再迁移？**
  - 现在跟进：提前消除弃用风险，但 `httpx2` 的成熟度、与 `TestClient` 的配合情况尚需验证。
  - 等到被迫迁移：省下当前工作量，但迁移会与 FastAPI 的大版本升级耦合在一起，风险更集中。
  - 这属于**依赖替换**（`AGENTS.md` §6 的不可逆决策范畴），**必须由项目所有者决定，不由实现者代决**。
- **阻塞**：测试依赖的锁定方式；`pyproject.toml` 中 `httpx` / `httpx2` 的取舍。

### E3. 数据库驱动与迁移工具

- **未定**：`asyncpg` 还是 `psycopg3`（async）；SQLAlchemy 2.x 的 async 用法细节。
- **已定**：PostgreSQL + Alembic 作为迁移工具（见 ADR-0008）。
- **阻塞**：`pyproject.toml` 的运行时依赖清单与首次迁移。

### E4. 生产环境是否需要离线依赖包

- **已定**：应用在容器内运行，**运行时不需要宿主机的 Python 与 uv**；交付物以镜像 tar + 运行脚本为主（交付物清单的具体形态随 ADR-0013 的交付形态变更另行确认，见 D2）。
- **已确认 / 不再是阻塞项**：内网 **PyPI 源可用且覆盖完整**——代理公共 PyPI，**真实安装过 wheel 成功**（见 D11）⇒ **构建时能装 wheel**。因此「是否额外交付一份离线 wheels / 离线 Python 运行时以便在宿主机上跑脚本或临时排障」**不再是阻塞项**：宿主机本身有 `python3`（见 D9），需要时也可走内网 PyPI 源装包。**本条只登记结论与证据类型，不写任何源地址。**
- **保留的一点**：上述能力是**构建期**的。**运行时仍不得依赖任何外部网络**（公网或内网源），见 `AGENTS.md` §8.5（前提表述已按 ADR-0013 更正）。
- **不阻塞**：交付物清单的最终形态——额外交付离线 wheels 至多是**可选项**，不是必需项。
