# 04 安全与审查

> **本册是「安全审查、鉴权口径与日志红线」的当前有效结论真源。**
> 只写：当前结论、当前实测证据、已否决方向、落地位置、未定项。
> **发件人身份、回复路由、启动即校验与审查接口契约**见 `specs/0001-email-forwarding-service/design.md`；本册只保留安全取向与合规边界。

## 结论

### 审查一期只做占位，上线时审查能力实际为零

- 安全审查（流① 审查出站、流④ 审查回复）一期实现为**「永远通过」的空实现**：**只定义接口与输出，不做任何真实检测**——不做敏感信息检测、不引入病毒扫描引擎、不接外部审查 API。
- 因此**一期上线时系统的审查能力实际为零**，这是一个**如实登记的合规风险**：真实审查接入前，本服务**不得被当作内容安全边界使用**，也不得对外声称具备安全审查能力。
- 空实现只提供接口与输出形状，**接口不承载任何真实判定语义**；审查流与发信流解耦（见下），所以后续把空实现换成真实实现时**不需要改动调用方**，只新增一个供应商实现。
- 审查流与发信流都不允许被跳过、短路，也不允许把审查失败当作通过处理——这类行为在本项目中属于**安全问题**而非普通缺陷。

### 唯一且必须保留的纪律：空实现必须被显式标注

- **必须在文档与代码注释中明确标注「这是空实现（永远通过）」**，标注位置至少覆盖 `providers/review/` 的接口与实现文件、审查相关配置说明，以及 `docs/security.md` 的安全边界一节。
- **在实现真实审查之前，不得对外声称系统具备安全审查能力**。不标注就会造成「系统已有安全审查」的误解。
- 这条纪律是审查部分**唯一靠人维持、删掉也不会有任何测试失败**的约束：空实现永远返回通过，删掉标注后功能测试与门禁仍然全绿。因此它必须被写进代码注释，而不能只留在这份册子里。

### 拒审链路一期虽不被触发，也必须建表预留

- `rejected` 表与「待审表 → 邮件表 / `rejected` 表」的完整状态流转**一期就要建出来**，尽管一期不会有任何记录真正被拒。
- 理由：审查通过 / 不通过的完整状态流转是主流程结构的一部分，缺表或缺状态会让后续补入审查能力时返工，也无法提前验证并发与状态流转。
- 已知代价：拒审路径在一期缺乏真实数据验证，「调用方如何得知被拒」只有在真实审查接入后才会被真正走到，届时可能暴露设计问题。

### 审查流与主流程解耦，不阻塞出站闭环

- 审查（流①）与发信（流②）是两条独立的进程内循环：审查只负责把记录推进到「可发信」状态，**不直接发信**。
- 因此一期只做空实现也**不阻塞端到端闭环**（提交 → 过审 → 发信 → 拉回 → 过审 → 查询回复），可以尽早验证调度、幂等抢占与 SMTP / IMAP 集成这些真正的风险点。
- 审查失败沿用本册之外的重试语义（次数、退避与终态失败的口径见 `docs/research/02-runtime-and-scheduling.md`，**本册不重复**）。

### API 鉴权：一期不做，但必须预留鉴权位置

- 服务**仅内网可达**，一期**不实现鉴权**；内网环境因而不需要鉴权。
- **但必须在 API 层预留鉴权位置**：后续实现时直接接入（挂到路由层），**不需要重排路由结构**，也不需要改端点路径。
- 风险如实登记：内网服务一旦跨网段暴露即为未授权可用，需与服务监听地址、端口与暴露范围一并评估。
- 后续**何时补、采用何种方式**（API Key / mTLS / 内网白名单）尚未决定，见未定项。

### 日志与信息红线

- **任何日志、CHANGELOG、异常信息、PR 描述都不得泄露**：邮件正文、附件内容、账号口令、收件人地址、原始 MIME。
- 排查需要定位某封邮件时，**用邮件 ID 引用，不贴正文**。
- 日志统一走 structlog，禁止 `print`；日志中不得出现收件人 / 发件人地址与邮箱账号。
- 配置只从配置层读取，禁止在模块里直接读环境变量；凭据只允许落在 `.env`（已被 gitignore）或其它被忽略的本地配置中，仓库内只允许占位符。
- 凭据不得打进容器镜像层或镜像内配置文件；镜像只应包含代码与占位模板。

## 实测证据

- `src/vs_email_forwarding/providers/review/` 目录已建、只有包占位文件；其模块说明已写明「一期审查是**永远通过的空实现**（占位）」。**接口协议已定案**（见 `specs/0001-email-forwarding-service/design.md`），**实现尚未落地**；真实审查将来采用本地规则还是外部审查服务仍未定案——那是一次**替换供应商实现**，不影响调用方。
- `src/vs_email_forwarding/config.py` 已含 `mail_from_address` 与 `reply_to_address` 两个字段（默认值为明显的假值），并保留 SMTP / IMAP 参数与四条业务流间隔字段；配置只从该模块读取。
- `.env.example` 已含 `MAIL_FROM_ADDRESS` 与 `REPLY_TO_ADDRESS` 两个键，并注明回复将被路由到专用回复邮箱、再由 IMAP 流拉回本服务。
- `src/vs_email_forwarding/api/v1/` 当前只挂载健康检查路由；投递与回复查询路由的契约见 `spec.md` 与 `specs/0001-email-forwarding-service/design.md`，代码尚未实现，**API 层当前没有任何鉴权依赖项**（这正是「位置已预留、实现未接入」的现状）。
- `docs/security.md` 已把「日志泄露、凭据硬编码、审查绕过、未授权投递、审查结果不可信、隔离约束被破坏、注入类问题」列为威胁类型，并写明一期审查是空实现占位、不要在真实审查接入前把本服务当作内容安全边界。
- 业务逻辑尚未实现：`providers/`、`flows/`、`db/` 下只有包占位文件，当前唯一可用端点是 `/healthz`。
- 门禁四项全绿（`ruff format --check`、`ruff check`、`mypy src`、`pytest`），即「空实现未接入」的现状并不表现为任何失败——这也印证了空实现的标注只能靠纪律维持。

## 已否决方向

- 一期就接入真实审查（本地规则 / 外部内容安全 API / 病毒扫描引擎）—— 原因：一期目标是先打通端到端闭环；外部 API 与「运行时不得依赖任何外部网络」冲突，本地病毒库还需额外的更新机制。
- 一期不建拒审链路 —— 原因：审查通过 / 不通过的完整状态流转是主流程的一部分，缺表会让后续实现返工。
- 等审查能力定了再动手做流水线 —— 原因：整条流水线会被一个尚未选型的依赖卡住；先做空实现占位可以不阻塞闭环验证。
- 把审查开关做成可硬编码关闭的旁路 —— 原因：审查被跳过或被短路属于安全问题，而不是「配置灵活性」。
