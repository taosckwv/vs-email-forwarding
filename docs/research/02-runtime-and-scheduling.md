# 02 运行时与数据流水线

> **本册是「调度、幂等与数据流水线」的当前有效结论真源。**
> 只写：当前结论、当前实测证据、已否决方向、落地位置、未定项。

## 主流程

```
DSH 会话
  │  POST /v1/messages
  ▼
待审表 (pending)
  │  流① 审查出站：敏感信息 / 病毒审查
  ├─ 通过 ──→ 邮件表 (queued)
  └─ 不通过 → 拒审表 (rejected)
                  │
                  │  流② 发信：查出未发送记录 → SMTP 投递
                  ▼
             （外部收件人）
                  │  回复
                  ▼
              专用回复邮箱
                  │  流③ 拉取入站：IMAP 拉取回复
                  ▼
              待审表 (inbound)
                  │  流④ 审查回复：同样的安全审查
                  ├─ 通过 ──→ 邮件表 (received)
                  └─ 不通过 → 拒审表
                                │
                                │  GET /v1/messages/{id}/replies
                                ▼
                            DSH 会话取回回复
```

上图是全项目最需要一眼看懂的东西：四条流各自的状态去向以此为准。

## 结论

- **调度载体**：四条流（流① 审查出站、流② 发信、流③ 拉取入站、流④ 审查回复）全部由**进程内 asyncio 后台任务**驱动，随 FastAPI 的 lifespan 启停，进程退出时任务被正确取消；不引入任何额外中间件，交付物中不含 broker，也没有第二个部署单元。
- **流的独立性**：四条流**并发运行**，各自拥有独立的循环、独立的开关、独立的间隔，并各自处理异常；单条流阻塞或抛异常都不影响其余三条。
- **并发上限（进程内 asyncio 的代价）**：单进程内的并发上限受 GIL 与事件循环影响；本场景负载是「每 10 秒一批记录」，**不构成瓶颈**。
- **代价：没有集中式的任务可视化与执行历史**（进程内 asyncio 不提供这类观测面）。
- **间隔与批量**：四条流的**默认间隔一律为 10 秒**；**间隔与每批处理条数都是配置项**，代码中不得出现硬编码的间隔数值或批量数值（**当前实现尚无批量字段，属待补**：`config.py` 与 `.env.example` 只有四个 `POLL_*_SECONDS`）。
- **间隔取舍（已定，风险由所有者承担）**：拉取入站流曾评估单独放长到 60 秒——IMAP 登录与拉取的单次成本远高于另外三条流，10 秒一次的频率存在触发企业邮箱风控或连接数限制的风险；所有者决定**四条流统一 10 秒**。间隔既然已是配置项，后续调整成本很低。
- **幂等抢占（硬约束）**：四条流的处理必须幂等；抢占任务一律使用 `SELECT ... FOR UPDATE SKIP LOCKED` 配合状态字段，并外加 `next_attempt_at` 控制退避。
- **禁止两步写法（硬约束）**：禁止「先 SELECT 判断、再 UPDATE」。当前只跑单实例也不放宽——四条流本身就是并发的，未来加实例时不允许重写数据访问层。
- **SQL 位置**：所有 SQL 只在仓储层（`src/vs_email_forwarding/db/`）；流处理层与路由层不得裸写 SQL，也不得直接拼 ORM 查询。
- **数据库**：PostgreSQL，生产、开发、测试三处一致。
- **部署形态**：生产 PostgreSQL 与应用**同机**，应用与数据库都跑容器、数据卷落在宿主机目录；当前为**单实例**部署，但抢占逻辑从第一天就按并发安全写。
- **多实例下 10 秒轮询会重复消费同一条记录（已登记的风险）**：所有者已知悉；当前按单实例部署，抢占逻辑仍按并发安全写，避免未来加实例时重写数据访问层。
- **运行环境前提**：生产环境与公网隔离、可达内网镜像源；运行时的隔离约束（不得依赖任何外部网络）见 `docs/research/01-delivery-and-deploy.md`——**真源在那里，本册不展开**。
- **库隔离**：开发库为 `vs_email_forwarding_dev`，测试库为 `vs_email_forwarding_test`，两者**分离**；集成测试允许清表，但绝不允许碰开发库。
- **测试用真库**：集成测试使用**真实 PostgreSQL**，不以 mock 替代数据库；mock 可保留为单元测试手段，但不能作为验证抢占与事务的唯一手段。
- **表形态（已定）**：待审表**由出站与入站共用一张**，用 `direction` 字段区分方向；审查不通过的记录**移入独立的 `rejected` 表**。因此物理表数量是 **3 张**（待审表、邮件表、`rejected` 表）。
- **附件**：一期**不支持附件**。
- **重试语义（硬约束）**：发送与审查都**最多 3 次**，退避 **15s / 30s / 60s**，之后进入**终态失败**并记录最后一次错误。
- **审查一期只做「永远通过」的空实现**（含接口与输出契约、以及拒审链路必须建表预留），**真源见 `docs/research/04-security-and-review.md`**。
- **进程重启的恢复**：进程重启会中断正在进行的 tick，恢复依赖数据库中的**状态字段**与 `next_attempt_at`，不依赖调度器本身。
- **可测性**：单次 tick 就是一个**普通的 async 函数**，测试里 `await` 一次即可验证整条流水线的推进，**不必等 10 秒**。
- **收信**：走 IMAP，**单个专用回复邮箱 + UID 游标增量拉取**，用 `References` / `In-Reply-To` 关联原邮件；**关联不上的邮件标记为孤儿但照样入库，不丢数据**。
- **入站幂等机制**：游标与幂等键**两者都要**——游标记录 `UIDVALIDITY` 与已处理的最大 UID（**游标管效率**）；独立于游标的唯一键为「**邮箱 + `UIDVALIDITY` + `UID`**」（**唯一键管正确性**）。**`Message-ID` 不得用作幂等键或去重依据**。
- **发信**：走 **SMTP 直连**（企业邮箱 / 自建 MTA），主机、端口、账号、口令、是否 STARTTLS 等参数**全部来自 `.env`**。
- **发信的 `From` 固定取服务配置、服务端显式写入 `Reply-To`**，**真源见 `docs/research/04-security-and-review.md`**。

## 实测证据

- 门禁与测试基线（四项全绿、`ruff` 告警口径等）见 `docs/research/03-dependencies-and-toolchain.md`；测试依赖的弃用提示见 `docs/open-questions.md` 的 E2。
- **业务逻辑尚未实现**：`src/vs_email_forwarding/flows/`、`src/vs_email_forwarding/db/`、`src/vs_email_forwarding/providers/` 下只有包占位文件，当前唯一可用的端点是 `/healthz`。
- **集成测试的依赖与覆盖重点已写明**：`tests/integration/` 需要真实 PostgreSQL（测试库）与本地邮件捕获服务，覆盖状态机转换、单次 tick 幂等、并发抢占不重复发信、回复关联四类最容易出错的路径。
- **开发库与测试库的初始化方式不同**：`compose.dev.yaml` 里只有开发库会在数据卷首次初始化时自动建出；测试库需要手工创建一次，该说明在文件末尾。
- **生产编排里数据库不向宿主机暴露端口**：`compose.yaml` 中应用容器内的数据库连接串被显式覆盖为 compose 服务名（容器内的回环地址指向应用自己），应用与数据库只走内部 bridge 网络。

## 已否决方向

- APScheduler（进程内、带持久化 job store） —— 对本场景多一层抽象，且测试单次 tick 需要手动触发 job，牺牲可测性；进程内 asyncio 已满足需求且无额外依赖。
- Celery + beat，或 Redis 队列 + worker —— 引入 broker 中间件与第二个部署单元；本项目是固定间隔的纯数据库轮询，进程内 asyncio 已满足需求且无额外依赖。
- 系统 cron / 计划任务调用内部 HTTP 端点 —— 与应用进程耦合弱，把「调度是否正确」变成运维配置问题，本地调试与自动化测试都更难。
- 单循环串行执行四条流 —— 牺牲并发：一条流阻塞会拖慢全部，而拉取入站流恰恰是最慢的一条。
- SQLite —— 不支持 `SELECT ... FOR UPDATE SKIP LOCKED`，写并发下锁库，无法满足幂等抢占。
- MySQL 8+ —— 同样支持 `SKIP LOCKED`，但在同一约束下 JSON 与部分索引的表达力与生态不如 PostgreSQL；项目已定 PostgreSQL。
- 一上来就做多实例 + 分布式锁 —— 当前是单实例，属过度设计；但数据访问层按并发安全写，未来加实例不用改。
- 用 mock 替代真实数据库做集成测试 —— 抢占用的是数据库语义（`SKIP LOCKED` 与事务），mock 验证不了；可保留为单元测试手段，但不能作为唯一手段。

## 落地位置

- `AGENTS.md` §3（门禁与开发依赖的命令入口）、§7（配置只从配置层读、时间用带时区 `datetime`、SQL 只在仓储层）、§8（四条流幂等、间隔不硬编码、发件人与 `Reply-To`、重试语义）；规则与结论的分工见其 §1 的文档导航表。
- `compose.yaml` —— 生产编排：应用与同机 PostgreSQL 由同一个 compose 管理，应用容器内覆盖数据库连接串，数据库不向宿主机暴露端口。
- `compose.dev.yaml` —— 开发依赖编排（PostgreSQL；本地邮件捕获服务是否最终采用仍待确认，见 `docs/open-questions.md`），开发库与测试库的初始化说明在文件末尾。
- `.env.example` —— 四条流间隔（`POLL_REVIEW_OUTBOUND_SECONDS`、`POLL_SEND_SECONDS`、`POLL_FETCH_INBOUND_SECONDS`、`POLL_REVIEW_INBOUND_SECONDS`）、数据库连接串与 `POSTGRES_*`、SMTP / IMAP 参数、发件人与回复地址；仓库只提交这一份模板。
- `src/vs_email_forwarding/config.py` —— 唯一的配置入口（pydantic-settings），四条流间隔字段的默认值为 10。
- `src/vs_email_forwarding/flows/` —— 四条流实现与调度器（目录已建，仅有占位文件）。
- `src/vs_email_forwarding/db/` —— ORM 模型、引擎与会话、仓储层（所有 SQL 都在这；目录已建，仅有占位文件）。
- `src/vs_email_forwarding/providers/` —— `smtp/`、`imap/`、`review/` 适配器，各自以 `base.py` 定接口；业务流程不得直接 import 具体实现库。
- `src/vs_email_forwarding/core/` —— 纯逻辑：消息 ID 生成、状态机、重试策略（不碰 I/O 与数据库）。
- `tests/integration/` —— 真实 PostgreSQL 与邮件回路的集成测试；`tests/unit/` 放不依赖数据库与网络的纯逻辑单测。
- `migrations/` —— Alembic 迁移入口（首次迁移待表字段清单确定）。
- `deploy/` —— 部署脚本与交付链的落点（新链路「服务器本地构建 + 基础镜像以 tar 带入」的脚本形态见未定项 D2）；`scripts/` 只放本地开发与门禁脚本。
