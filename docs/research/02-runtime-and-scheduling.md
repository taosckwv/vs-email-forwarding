# 02 运行时与调度

> **本册是「调度载体、幂等抢占与重试语义」的当前有效结论真源。**
> 只写：当前结论、当前实测证据、已否决方向、落地位置、未定项。
> **本特性的数据模型、流水线细节与依赖选型**见 `specs/0001-email-forwarding-service/design.md`；本册只保留**跨特性底座**，不复述那边的结论。

## 主流程

**主流程图**见 `specs/0001-email-forwarding-service/design.md` 的「概览」一节（DSH 会话 → 待审表 → 审查 / 发信 / 拉取 / 审查回复 → 邮件表 / 拒审表 → 调用方取回复）：四条业务流各自的状态去向以那张图为准，本册不复述图本身。

## 结论

- **调度载体**：**全部后台任务**都由**进程内 asyncio 后台任务**驱动——四条业务流（流① 审查出站、流② 发信、流③ 拉取入站、流④ 审查回复）加上保留期清理这一条；它们随 FastAPI 的 lifespan 启停，进程退出时任务被正确取消；不引入任何额外中间件，交付物中不含 broker，也没有第二个部署单元。
- **流的独立性**：各条流**并发运行**，各自拥有独立的循环与独立的间隔，并各自处理异常；单条流阻塞或抛异常都不影响其余各条。**一期没有「关掉某条流」的运行时配置**：审查实现只能由 `providers/review/` 的工厂在测试里替换（属测试注入点），把审查流短路或关掉属安全边界问题，见 `docs/security.md`。
- **并发上限（进程内 asyncio 的代价）**：单进程内的并发上限受 GIL 与事件循环影响；本场景负载是「每 10 秒一批记录」，**不构成瓶颈**。
- **代价：没有集中式的任务可视化与执行历史**（进程内 asyncio 不提供这类观测面）。
- **间隔与批量**：四条业务流的**默认间隔一律为 10 秒**；**间隔与每批处理条数都是配置项**，代码中不得出现硬编码的间隔数值或批量数值（`config.py` 与 `.env.example` 已含六个间隔项——四个 `POLL_*_SECONDS` 加 `POLL_CLEANUP_SECONDS`——与 `BATCH_SIZE`（每批条数，默认 100，五条流共用；流③ 也用它限制单个 tick 拉取的封数），另有三个单次调用超时、两项内容长度上限与回复分页条数；完整清单见 `specs/0001-email-forwarding-service/design.md` 的配置项清单）。
- **间隔取舍（已定，风险由所有者承担）**：拉取入站流曾评估单独放长到 60 秒——IMAP 登录与拉取的单次成本远高于另外三条流，10 秒一次的频率存在触发企业邮箱风控或连接数限制的风险；所有者决定**四条业务流统一 10 秒**。间隔既然已是配置项，后续调整成本很低。
- **幂等抢占（硬约束）**：四条业务流（外加保留期清理）的处理必须幂等；抢占任务一律使用 `SELECT ... FOR UPDATE SKIP LOCKED` 配合状态字段，并外加 `next_attempt_at` 控制退避。
- **禁止两步写法（硬约束）**：禁止「先 SELECT 判断、再 UPDATE」。当前只跑单实例也不放宽——这些流本身就是并发的，未来加实例时不允许重写数据访问层。
- **SQL 位置**：所有 SQL 只在仓储层（`src/vs_email_forwarding/db/`）；用例层、流处理层与路由层不得裸写 SQL，也不得直接拼 ORM 查询。
- **数据库**：PostgreSQL，生产、开发、测试三处一致。
- **引擎与会话的生命周期（已定）**：引擎是进程级单例（lifespan 创建、退出时 `dispose()`），API 请求与五条后台任务都**按阶段开短会话**、用完即关，会话不跨网络调用、不跨任务共享；连接池用 SQLAlchemy 默认口径。仓储层由调用方传入会话，事务边界属于 `service/` 与 `flows/`——结论与已否决方向见 `docs/architecture.md` §5。
- **部署形态**：生产 PostgreSQL 与应用**同机**，应用与数据库都跑容器、数据卷落在宿主机目录；当前为**单实例**部署，但抢占逻辑从第一天就按并发安全写。
- **多实例下 10 秒轮询会重复消费同一条记录（已登记的风险）**：所有者已知悉；当前按单实例部署，抢占逻辑仍按并发安全写，避免未来加实例时重写数据访问层。
- **运行环境前提**：生产环境与公网隔离、可达内网镜像源；运行时的隔离约束（不得依赖任何外部网络）见 `docs/research/01-delivery-and-deploy.md`——**真源在那里，本册不展开**。
- **库隔离**：开发库为 `vs_email_forwarding_dev`，测试库为 `vs_email_forwarding_test`，两者**分离**；集成测试允许清表，但绝不允许碰开发库。
- **测试用真库**：集成测试使用**真实 PostgreSQL**，不以 mock 替代数据库；mock 可保留为单元测试手段，但不能作为验证抢占与事务的唯一手段。
- **保留期清理的调度地位（已定）**：它是**第 5 条进程内后台任务**，与四条业务流同构（独立循环、独立开关、独立间隔、分批 `FOR UPDATE SKIP LOCKED` 删除），随 lifespan 启停；**清理范围、清理间隔配置项与级联删除见 `specs/0001-email-forwarding-service/design.md`**。
- **重试语义（硬约束）**：发送与审查都**最多 3 次重试**（首次尝试 + 3 次重试，合计最多 4 次尝试），退避 **15s / 30s / 60s**，之后进入**终态失败**并记录最后一次错误。认领谓词因此是 `attempt_count <= 4`：第 4 次尝试被认领后崩溃、结果尚未提交的行，由**各条流自身的认领逻辑收割**为终态（不递增计数、不发起第 5 次调用、也不新增第 6 条后台任务）；没有这一支，该行会永久卡在待处理状态（结论与实现口径见 `specs/0001-email-forwarding-service/design.md` 的流水线一节）。
- **审查一期只做「永远通过」的空实现**：安全取向与合规风险登记见 `docs/research/04-security-and-review.md`，接口与输出契约见 `specs/0001-email-forwarding-service/design.md`。
- **进程重启的恢复**：进程重启会中断正在进行的 tick，恢复依赖数据库中的**状态字段**与 `next_attempt_at`，不依赖调度器本身。
- **可测性**：单次 tick 就是一个**普通的 async 函数**，测试里 `await` 一次即可验证整条流水线的推进，**不必等 10 秒**。

## 已否决方向

- APScheduler（进程内、带持久化 job store） —— 对本场景多一层抽象，且测试单次 tick 需要手动触发 job，牺牲可测性；进程内 asyncio 已满足需求且无额外依赖。
- Celery + beat，或 Redis 队列 + worker —— 引入 broker 中间件与第二个部署单元；本项目是固定间隔的纯数据库轮询，进程内 asyncio 已满足需求且无额外依赖。
- 系统 cron / 计划任务调用内部 HTTP 端点 —— 与应用进程耦合弱，把「调度是否正确」变成运维配置问题，本地调试与自动化测试都更难。
- 单循环串行执行四条业务流 —— 牺牲并发：一条流阻塞会拖慢全部，而拉取入站流恰恰是最慢的一条。
- SQLite —— 不支持 `SELECT ... FOR UPDATE SKIP LOCKED`，写并发下锁库，无法满足幂等抢占。
- MySQL 8+ —— 同样支持 `SKIP LOCKED`，但在同一约束下 JSON 与部分索引的表达力与生态不如 PostgreSQL；项目已定 PostgreSQL。
- 一上来就做多实例 + 分布式锁 —— 当前是单实例，属过度设计；但数据访问层按并发安全写，未来加实例不用改。
- 用 mock 替代真实数据库做集成测试 —— 抢占用的是数据库语义（`SKIP LOCKED` 与事务），mock 验证不了；可保留为单元测试手段，但不能作为唯一手段。
- 把保留期清理搭在既有某条流的 tick 末尾 —— 两件事被绑在同一个间隔上，想调清理频率就得动发信或拉取频率，破坏「四条业务流各自独立、互不影响」的结论。
- 把保留期清理交给外部计划任务（宿主 cron / 容器 entrypoint 里的定时命令）—— 把「清理是否正确」变成运维配置问题，本地调试与自动化测试都更难（本册已否决过同类做法）。
