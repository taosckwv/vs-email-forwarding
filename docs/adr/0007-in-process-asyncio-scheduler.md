# 0007. 进程内 asyncio 四流调度

- 状态：已接受
- 日期：2026-09-29
- 决策者：项目所有者

## 背景

服务的核心是一条流水线，由四条定时轮询流组成：

| 流 | 职责 |
|---|---|
| 流① 审查出站 | 从待审表取出出站邮件，做敏感信息 / 病毒审查；通过则写入邮件表，不通过则移入拒审表 |
| 流② 发信 | 查询邮件表中未发送的记录，通过 SMTP 投递 |
| 流③ 拉取入站 | 通过 IMAP 从专用回复邮箱增量拉取回复，落入待审表 |
| 流④ 审查回复 | 对拉回的回复做同样的审查，通过则写入邮件表 |

需要决定调度载体，以及四条流是并发还是串行。

## 决策

- **进程内 asyncio 后台任务**，随 FastAPI 的 lifespan 启停。
- **四条流并发，各自独立的循环、独立的开关、独立的间隔**，每条流有独立的异常处理，**单流异常不影响其他流**。
- **默认间隔全部为 10 秒**，但**间隔、每批处理条数一律是配置项，不得把 `10` 写死在代码里**。
- 关闭与启动遵循 lifespan 生命周期，保证进程退出时任务被正确取消。

### 已知的权衡（所有者明确选择）

拉取邮件流的成本远高于其他三条——**IMAP 登录与拉取比数据库查询贵得多**，10 秒一次的频率存在触发企业邮箱风控或连接数限制的风险。曾建议将该流单独拉长到 60 秒，**所有者明确选择四条流全部 10 秒**。间隔既然已是配置项，后续调整成本很低。

## 后果

### 正面

- **不需要任何额外中间件**：没有 Redis、没有 broker、没有第二个部署单元。这与「完全离线 + 交付物只有镜像 tar」的部署形态（ADR-0005）高度契合。
- **可测性是本决策最大的收益**：单次 tick 就是一个普通的 async 函数，测试里 `await` 一次即可验证整条流水线的推进，**不必等 10 秒**。这让状态机转换、抢占幂等性、重复发信防护、回复关联这些最容易出错的地方都能被真实测试覆盖。
- 四条流互不阻塞：拉取邮件流即使因为网络慢而耗时，也不会拖慢发信流的节奏。

### 负面 / 代价

- 调度与 Web 进程同生命周期：**进程重启会中断正在进行的 tick**。可靠性依赖数据库中的状态字段与 `next_attempt_at` 在做恢复，而不是依赖调度器本身。
- 没有集中式的任务可视化与执行历史（APScheduler 或外部队列能提供这类能力）。
- 单进程内的并发上限受 GIL 与事件循环影响；由于负载是「每 10 秒一批数据库记录」，这不是实际瓶颈。
- 拉取流 10 秒一次的风控风险由所有者承担（见上）。

## 备选方案与被否决的原因

| 方案 | 否决原因 |
|---|---|
| APScheduler（进程内，带持久化 job store） | 成熟库、自带 job 持久化与可视化；但对本场景多了一层抽象，且**测试单次 tick 需要手动触发 job**，牺牲了本决策最看重的可测性。作为折中方案曾被提出，未被采纳。 |
| Celery + beat，或 Redis 队列 + worker | 适合多实例与高吞吐。但本场景是「10 秒间隔 + 纯数据库轮询」，引入 broker 属于过度设计，并且会新增一个部署依赖——在完全离线的交付模式下，每多一个组件都要多一个镜像 tar 与一套部署步骤。 |
| 系统 cron / 计划任务调用内部 HTTP 端点 | 运维直观，但与应用进程耦合弱，本地开发调试麻烦，且不易测；同时把「调度是否正确」变成了运维配置问题。 |
| 单循环串行执行四条流 | 时序最确定、最好调试，但一条流阻塞会拖慢全部，而拉取邮件流恰恰是最慢的一条。 |
