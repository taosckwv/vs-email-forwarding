# 0012. 发件人身份与回复路由

- 状态：已接受
- 日期：2026-09-29
- 决策者：项目所有者

## 背景

内容形态已定：只有纯文本 / HTML，**没有抄送密送、也没有自定义邮件头**。因此「回复能否回到可被 IMAP 拉取的信箱」只取决于 `Reply-To` 或 `From` 是否指向那个信箱。

### 此处纠正一个先前的错误表述

此前的说法是「回复能否回来**完全取决于服务端是否强制写 `Reply-To`**」。**这不准确**：

> 按 RFC 5322，收件人点击「回复」时，客户端把回复发往 `Reply-To`（若存在），否则发往 `From`。既有实现的 `From` **恰好就是 IMAP 拉取的那个信箱**，所以**回复回路本来就是通的，并不依赖是否强制写 `Reply-To`**。

把这个纠正如实记录下来是有意义的：它**改变了决策的性质**——写 `Reply-To` 不是「让回路能通」的必需条件，而是「让回路不会因为后续改动而静默断掉」的**加固手段**。

## 决策

1. **`From` 固定取服务配置**（配置项 `MAIL_FROM_ADDRESS`），**不允许调用方传入**。
2. **服务端显式写入 `Reply-To`**，其值等于 IMAP 拉取所用的信箱（配置项 `REPLY_TO_ADDRESS`）。

> 文档中一律使用占位符表示地址（如 `<from-address>`、`<robot-mailbox>`）。**仓库内不出现任何真实邮箱地址、主机名或账号**（`AGENTS.md` §10）。

### 为什么 `From` 必须固定

- **安全**：若调用方可以任意指定发件人，本服务就成了**可伪造任意发件人的工具**。
- **可观测性**：`From` 一旦与 IMAP 拉取的信箱不一致，回复回路会**静默**断掉——没有报错、没有告警，只是回复再也不会回来。把 `From` 固定成配置项，等于把这个变量从系统里移除。

### 为什么在 `From` 已经指向该信箱的前提下，仍然要显式写 `Reply-To`

理由不是「否则回路不通」（见背景），而是**把隐式正确变成显式锁定**：

- 把「回复去哪」从「依赖 `From` 恰好配得对」变成一行被显式声明的邮件头；
- 将来对外发件身份需要变更时（例如改成 `noreply@…`、或某个部门别名），回复**仍必须回到可拉取的信箱**。此时显式声明的 `Reply-To` 比隐式推导更难被后续改动破坏：**改了 `From` 也不会顺手把回复路由改坏**。

## 未决部分（留待需求阶段，本 ADR 不决定）

- **如何保证 `REPLY_TO_ADDRESS` 与 IMAP 账号一致**：启动即失败（fail fast）、启动时告警、还是仅靠人工保证？
- **IMAP 登录名不是邮箱地址时的映射方式**：此时「IMAP 账号」与「信箱地址」不是同一个字符串，需要一条明确的映射规则。

本 ADR 只锁定一点：**必须显式写 `Reply-To`**。上述两项记录在 `docs/open-questions.md` B1，**不由实现者代决**。

## 后果

### 正面

- 回复路由由**服务端**保证，不依赖调用方行为；调用方也无法伪造发件人。
- 对外发件身份可以独立演进，而回复回路不受影响（有 `Reply-To` 兜住）。
- 故障模式从「静默断掉」变成「一个显式配置项」——可被检查、可被校验。

### 负面 / 代价

- 多一个必填配置项（`REPLY_TO_ADDRESS`），漏配就少一层保障。
- 若 IMAP 登录名不是邮箱地址，需要额外映射（留需求阶段）。
- **因为不写 `Reply-To` 也能通，这条决策的价值要靠纪律维持**：未来若有人以「简化配置」为由删掉 `Reply-To`，功能测试**仍然会通过**，只有在 `From` 发生变更时才会暴露问题。因此建议在需求阶段把上述「一致性保证方式」定下来，用启动校验把它变成硬约束。

## 备选方案与被否决的原因

| 方案 | 否决原因 |
|---|---|
| 不写 `Reply-To`，完全依赖 `From` | 行为隐式依赖两个配置恰好相等；任何一次改 `From` 都会**静默**断掉回复回路（无报错、无告警）。 |
| 允许调用方指定 `From` | **安全否决**：本服务会变成可伪造任意发件人的工具；且 `From` 与 IMAP 信箱不一致时回复静默丢失。 |
| 允许调用方指定 `Reply-To` | 同上，等于绕过服务端对回复路由的保证；且「不支持自定义邮件头」这一已定边界会被破坏。 |
