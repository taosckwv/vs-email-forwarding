# 0008. PostgreSQL 与幂等抢占

- 状态：已接受
- 日期：2026-09-29
- 决策者：项目所有者

## 背景

数据必须落库：投递记录与邮件正文元数据是「用户说没收到邮件」时唯一的排查依据，也是审计与重放的基础。此外，四条流（见 ADR-0007）会并发地从同一张表里抢任务，如果抢占方式不正确，同一封邮件会被审查两次、发送两次。

部署形态已定为单实例内网进程、多客户端调用（ADR-0005）。所有者知悉：**多实例下 10 秒轮询会重复消费同一条记录**。

## 决策

- **数据库：PostgreSQL**。
- **开发、预演、生产环境全部容器化**：开发机通过 compose 起 PostgreSQL，生产与预演同样跑容器（生产数据卷挂载宿主机目录）。
- **单实例部署，但从第一天起就按并发安全的方式写抢占逻辑**：
  - 抢占任务一律使用 **`SELECT ... FOR UPDATE SKIP LOCKED`** 配合状态字段（外加 `next_attempt_at` 控制退避）。
  - **禁止「先 SELECT 判断、再 UPDATE」的两步写法。**
  - 理由：四条流本身就是并发的，而且未来若要加实例，不允许重写数据访问层。
- **开发库与测试库分离**：`vs_email_forwarding_dev` 与 `vs_email_forwarding_test`。
- **测试使用真实 PostgreSQL**，不以 mock 替代数据库。测试重点覆盖四类最易出错的路径：
  1. 状态机转换；
  2. 单次 tick 的幂等性（重复执行不产生副作用）；
  3. 并发抢占不导致重复发信；
  4. 回复与原邮件的关联。

## 后果

### 正面

- 并发安全从第一天就是正确的，未来水平扩展只需加实例，不需要改数据访问层。
- 集成测试能覆盖抢占与事务这类**最不容易靠人工发现、也最容易被 mock 掩盖**的问题。
- PostgreSQL 的 `SKIP LOCKED`、`JSONB`、部分索引等能力都能用上。

### 负面 / 代价

- **开发与测试强依赖容器**：本机当前没有 Docker，必须先安装 Docker Desktop（需要管理员权限、WSL2，可能重启）。在装上之前，集成测试与开发环境都跑不起来。该未定项记录在 `docs/open-questions.md` D3。
- 集成测试比纯 mock 单测慢，需要真实数据库的连接与事务。
- 数据卷持久化需要额外关注容器内 `postgres` 用户的 uid 与宿主机目录权限。

## 备选方案与被否决的原因

| 方案 | 否决原因 |
|---|---|
| SQLite | 零部署成本，但写并发下会锁库，不适合「定时轮询 + 多流并发写」的场景，只适合本地单测。 |
| MySQL 8+ | 同样支持 `SKIP LOCKED`，若内网只有 MySQL 也够用；但 JSON 与部分索引的使用体验差一截，而本项目有较多元数据字段。 |
| 用 mock 替代数据库做测试 | 跑得快、零环境依赖，但恰好盖不住抢占与事务逻辑——也就是最容易出错的那些地方。可保留为单元测试手段，但不能作为唯一手段。 |
| 一上来就做多实例 + 分布式锁 | 所有者选择单实例；但抢占逻辑按并发安全写，等价于提前满足了多实例的必要条件。 |
