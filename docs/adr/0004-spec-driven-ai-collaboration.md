# 0004. AI 协同开发模型：规格驱动 + AGENTS.md 唯一真源

- 状态：已接受
- 日期：2026-09-29
- 决策者：项目所有者

## 背景

项目所有者把「怎么让 AI 协同开发」作为一等需求提出，而不是附带要求。这意味着仓库结构必须为「AI 能够被约束、产出能够被审查」而设计。

核心判断：AI 协作的真实失败模式**不是「不会写代码」，而是「不知道边界在哪、不知道验收标准是什么」**。因此投入应当花在边界与验收标准的表达上，而不是花在更花哨的提示词上。

## 决策

采用**规格驱动**的档位（三档中的中间档）：

1. **`AGENTS.md`（仓库根）是 AI 规则的唯一真源。** 其他 AI 工具的配置文件（当前是 `CLAUDE.md`）**只做指向，不复制内容**——规则一旦存在两份，早晚漂移，导致不同工具行为不一致。
2. **按目录分层的局部 `AGENTS.md`**：agent 深入到某个模块时能读到就近约束，而不是只能读根目录那一份。
3. **`specs/<NNNN-slug>/{spec.md, plan.md, tasks.md}`**，强制流程为「**先写规格 → 所有者确认 → 再实现**」。模板放在 `specs/_template/`，禁止自造格式。
4. **`docs/adr/` 记录不可逆决策**，只记决策与理由，不记实现细节。
5. **PR 模板强制关联 spec 编号**，涉及不可逆决策时同时关联 ADR。
6. **`skills/` 固化关键流程**：把有固定步骤、固定验收标准的工作（例如「新增一个审查供应商」「新增一个 SMTP 供应商」「离线发版」）写成仓库内可复用的 skill，使 AI 每次执行路径一致、可复现、可审查。
7. **质量门禁落在 pre-commit + 一键脚本**（见 ADR-0010）。

## 后果

### 正面

- 每次改动都能追溯到「哪条规格、哪条验收标准」，产出可被审查，而不是看一个黑盒 diff。
- 目录职责表把「该放哪层、不该放哪层」写死，agent 改错层一眼可见。
- 规则只有一处可改，多工具（DSH / Claude / 其他）行为一致。
- `skills/` 把重复流程的执行路径固定下来，是 AI 协同中杠杆最高的部分。

### 负面 / 代价

- 每个非平凡特性要多写三份文档（spec / plan / tasks），前期开销明显。
- 流程要求「所有者确认规格后才能实现」，因此**无法完全无人值守**，必须有人参与确认。
- 规格与代码可能出现不一致，需要靠验收环节与「以代码为准、并提一个修正文档的改动」的约定来收敛。
- 骨架阶段就要求建立 `specs/` 与 `skills/` 目录，在需求尚未开始时这两个目录是空的（仅放说明文件），看起来像过度设计。

## 备选方案与被否决的原因

| 方案 | 否决原因 |
|---|---|
| 轻量档（仅根 `AGENTS.md` + `docs/adr/` + `CONTRIBUTING`） | AI 靠读代码自行理解意图，产出可审查性弱；`AGENTS.md` 无法表达单个特性的验收标准。 |
| 重型档（轻量/规格驱动之上再加 RFC 编号流程、逐变更评审清单） | 对单人项目过重，评审清单会退化为形式主义。 |
| 每类 AI 工具各自维护一份规则配置 | 充分利用各工具特性，但多处规则会随时间长歪，导致同一问题在不同工具下行为不一致。这是本决策明确要避免的失败模式。 |
| 不做分层，只在根目录放一份 `AGENTS.md` | 最简单，但 agent 深入某个目录时得不到局部约束，容易跨层写代码（例如在路由层裸写 SQL）。 |
