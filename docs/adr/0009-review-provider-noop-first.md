# 0009. 一期安全审查为空实现占位

- 状态：已接受
- 日期：2026-09-29
- 决策者：项目所有者

## 背景

流水线中流①（审查出站）与流④（审查回复）都要做安全审查：敏感信息检查与病毒检查。但审查能力的来源尚未确定——本地规则（敏感词库 + 正则）、本地病毒扫描（ClamAV / clamd）、还是外部内容安全 API，都需要额外的选型与资源。

如果等审查能力定了再动手，整条流水线都无法开工。

## 决策

- **一期将安全审查实现为「永远通过」的空实现占位**，接口（审查供应商抽象）先留好，调用方按接口编程。
- 拒审链路（拒审表与状态流转）**仍需建表与预留**，尽管一期不会被真实触发。
- 真实的审查实现留待后续规格阶段确定。

### 与此相关的已知冲突（必须在补齐审查能力前解决）

生产服务器**完全离线**（ADR-0005），因此：

- **「调用外部内容安全 API」与离线前提直接冲突**。若采用该方案，需要内网自建审查服务，或者重新评估离线约束。
- 若采用**本地病毒库**（如 ClamAV），则**病毒库的离线更新机制**需要单独设计——离线服务器无法自动拉取病毒库更新，这会直接影响审查的有效性。
- 因此真实审查能力的落地不只是「选一个库」，而是要连更新链路一起设计。

## 后果

### 正面

- 不阻塞主流程：一期可以端到端跑通完整闭环（提交 → 过审 → 发信 → 拉回 → 过审 → 查询回复），从而尽早验证调度、抢占、SMTP/IMAP 集成这些真正的风险点。
- 接口一旦定下，后续替换实现**不需要改动调用方**，只新增一个供应商实现。
- 开发与集成测试不需要真实的病毒样本与敏感词库。

### 负面 / 代价

- **一期上线时安全审查实际上是零**，存在合规风险，必须在真实上量前补齐。
- 拒审链路缺乏真实数据验证：拒审表、拒审状态、以及「调用方如何得知被拒」都只会在补齐审查后才真正被走到，届时可能暴露设计问题。
- 「空实现永远通过」这一事实若被遗忘，容易造成「系统已有安全审查」的误解。因此必须在文档与代码注释中明确标注，并且在实现真实审查前不得对外声称具备该能力。

## 备选方案与被否决的原因

| 方案 | 否决原因 |
|---|---|
| 一期实现本地规则（敏感词库 + 正则，可选 clamd） | 词库与规则尚未确定，且规则质量直接决定误判率；在需求阶段之前实现等于替所有者做决定。 |
| 一期调用外部内容安全 API | 依赖与配额未定，且与「生产完全离线」冲突。 |
| 一期干脆不做审查流与拒审表 | 会让流水线结构与最终形态不一致，后续补入时等于重构；而且无法提前验证并发与状态流转。 |
