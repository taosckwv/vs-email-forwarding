# 测试规范

> **本文件是测试规范与测试说明的唯一出处**：单测与集成测试的分工判据、写测试的硬规则、AI 写测试的作业流程、评审检查表、pytest 标记约定。
> 门禁**怎么跑**（五步、每步的命令与失败行为）见 `scripts/README.md`；门禁**什么算合格**与工具选型见 `docs/research/03-dependencies-and-toolchain.md`；逐条 `AC-n` 的测试落点是**各特性的** `specs/<特性>/plan.md`（本文件不复述，也不收录逐条映射表）。
> 每层**放什么 / 不放什么**见 `AGENTS.md` §4 与各目录自己的 `README.md`。写作规范见 `docs/README.md` §4。

## 1. 第一原则

**测试是可执行的规格（oracle），不是覆盖率的副产品。** 判一个测试是否成立只看三条：

| 判据 | 含义 | 不成立的样子 |
|---|---|---|
| **能失败** | 把被测逻辑改错，它会红 | 断言与实现同步，恒绿 |
| **期望值独立** | 期望值来自规格 / 决策表 / 人工推导，**不来自被测代码** | `assert f(x) == f(x)` |
| **可追溯** | 每条测试指向一条业务规则、`AC-n`、不变量或失败路径 | 说不出它在验证什么 |

> **红线判据**：*把被测实现改错（或改回旧行为），测试仍然通过——它不是测试，是噪声。*
> 这条判据解释了门禁为什么在 `pytest` 之外还有一步变异测试：覆盖率看不出这件事，变异测试看得出（依据见 `docs/research/03-dependencies-and-toolchain.md`）。

## 2. 硬规则

| 编号 | 规则 |
|---|---|
| **R1** | 每条测试必须能回答「它在验证哪条业务规则 / `AC-n` / 不变量 / 失败路径」。**答不出就不写**。 |
| **R2** | **期望值只能来自规格、决策表、人工推导、独立参考实现，或经人工确认过的夹具数据**；禁止调用被测代码（含其内部函数）生成期望值，也禁止把被测逻辑在测试里重写一遍当参照。 |
| **R3** | **没有红过的测试不算测试。** 新增测试必须留下失败证据：TDD 的先红，或实现完成后的一次故意破坏 / 变异实验（证据写进 PR 描述）。 |
| **R4** | 测试文件（尤其断言、期望值、`skip`、删除）的改动是**一等评审项**，必须能单独被看见并说明理由。 |
| **R5** | 禁止空洞断言：`assert x is not None`、`assert len(x) >= 0`、只断言「没抛异常」、`pytest.raises(Exception)` 这类过宽的异常断言。 |
| **R6** | 禁止 mock 被测对象自身及其内部实现细节；测试替身只允许出现在**进程 / 网络 / 第三方**边界（§3.5、§4.2）。 |
| **R7** | 禁止无解释的魔数：期望值必须带业务含义（例：`# 拒审状态不产生任何 SMTP 投递`）。 |
| **R8** | 禁止用 `skip` / `xfail` / 删除 / 降低断言强度 / 延长超时 / 加重试来把失败变绿。**集成用例因容器未起而跳过是标记机制的正常行为，不是「用 skip 换绿」**（§8）。 |
| **R9** | 覆盖率是诊断指标，**不得单独作为验收门槛**；测试数量与断言数量**不得作为考核目标**。 |
| **R10** | 夹具数据（`tests/fixtures/`）一旦成为期望值来源，它就等同于断言：修改夹具必须按 R4 评审。 |
| **R11** | `AGENTS.md` §8 的每一条硬约束（幂等、抢占、`From` / `Reply-To`、日志与信息红线、重试语义、无外网依赖等），**至少要有一条测试在违反它时会失败**；约束的取值以 `docs/research/` 对应主题册为唯一出处，测试文件里不复述数字，只引用。 |
| **R12** | 测试必须可乱序、可并行、可重复：不依赖执行顺序、全局状态、真实时间推进与外部网络。 |
| **R13** | 设计契约（如 `design.md`）里被点名「必须同时成立 / 不得删除」的**配置行**，**可能没有自动检查兜底**：评审须逐条回到代码确认该配置行仍在、且与契约一致，不得以「门禁全绿」代替这条核对（§7 检查表）。 |

## 3. 单元测试（`tests/unit/`）

### 3.1 该写什么、不写什么

- **写**：业务规则与决策表、状态迁移、边界与等价类、错误与拒绝路径、幂等与重试语义、金额 / 计数 / 时间的取整与时区、纯函数的不变量。`core/` 是纯逻辑层（`docs/architecture.md` §2），它必须能被单测直接调用。
- **不写**：getter / setter、数据类字段访问、框架与第三方库自身行为、生成代码、纯 DTO 序列化，以及「只为了提高覆盖率」的分支堆砌。
- **配额原则**：测试条数与业务规则条数量级匹配（n 条规则 → 约 n 条行为测试，另加边界与失败路径）。**一个规则写十条 happy path 测试属于灌水。**

### 3.2 命名与结构

- 命名：`test_<行为>_<条件>_<预期>`，例 `test_submit_rejects_recipient_when_missing`。
- 结构：Arrange–Act–Assert，三段不混。
- **一个测试只判定一个行为**。可以有多条断言，但必须服务于同一次行为判定；禁止「断言轮盘」（一个方法里塞一堆互不相关的断言，失败后不知道是谁挂的）。
- 测试名要让失败信息自解释：不打开代码就知道哪条业务规则被破坏。

### 3.3 期望值必须独立推导

反例（这是 AI 最容易写出来的形状）：

```python
def test_retry_backoff() -> None:
    # ❌ 期望值由被测代码自己算出来：断言等于把实现复制一遍
    expected = next_retry_delay(attempt=2)
    assert next_retry_delay(attempt=2) == expected
```

正例（期望值来自规格）：

```python
def test_retry_backoff_second_retry_waits_30s() -> None:
    # 退避表是服务固定语义，取值见 docs/research/02-runtime-and-scheduling.md
    assert next_retry_delay(attempt=2) == 30
```

需要更强的 oracle 时，按优先级选择：

1. **规格 / 决策表**推导出的具体值（首选）；
2. **属性测试**：不变量、往返（encode→decode 复原）、幂等（`f(f(x)) == f(x)`）、守恒（总额不变）、单调性——天然不依赖实现，是绕开 oracle 难题的最佳工具；
3. **差分对比**：与经过人工确认的独立参考实现 / 旧版本对比；
4. **夹具数据**：首次引入必须人工逐条过目（此后修改即 R4）。

### 3.4 边界表

写测试前先列出边界：`<=` / `<` / `==` / 空 / 单元素 / 最大最小 / 零 / 负数 / 闰年 / 时区与 DST / 精度溢出 / Unicode。
**边界两侧都要测**：只测 `day == 0` 杀不掉 `day < 1` 被改成 `day <= 1` 的缺陷——必须有 `day == 1` 这条。

### 3.5 测试替身

- 优先级 **fake > stub > mock**：能用一个真的内存实现就用真的。
- 替身只用于**单测里不该触碰的边界**（时钟、随机源、外部进程），且**替身的方法必须真实存在于契约上**——`providers/*/base.py` 是这些契约的落点（`docs/architecture.md` §2）。
- **不要断言调用次数**，除非「调用次数本身就是业务规则」（重试次数、限流、去重后只投递一次）。
- 不要断言调用顺序，除非顺序本身是业务契约。
- 判据：*一条断言在任何真实实现被替换时都不会失败，它测的就是替身，删掉。*

### 3.6 确定性与断言

- 注入时钟、随机种子、ID 生成器、配置；**禁止 `sleep`**、禁止依赖真实时间推进。
- 断言具体的值 / 结构 / 顺序 / 错误码 / 副作用；失败信息带上输入与预期。
- 异常用例断言**具体异常类型 + 错误码或关键字段**，不用裸 `Exception`。

## 4. 集成测试（`tests/integration/`）

### 4.1 边界与真实依赖

集成测试验证的是**跨边界的真实协作**：数据库、SMTP / IMAP、HTTP、文件、时钟、并发。

- 放哪一层：**判据只有一条——这条断言需不需要真实数据库或真实邮件服务。** 需要就是集成测试，否则是单测（`AGENTS.md` §4 的目录职责）。
- **用真实依赖**：真实 PostgreSQL、真实邮件服务（GreenMail），由 `scripts/dev-up.sh` 提供；**不用 mock 替代数据库**——抢占与事务用的是数据库语义，替身验证不了（结论与理由见 `docs/research/02-runtime-and-scheduling.md`，本文件不复述）。测试库与开发库严格分离，**集成分支绝不允许碰开发库**。

### 4.2 替身只允许出现在哪

- 只替换**测试环境跑不了、且不是本次验证目标**的第三方进程（例如外部审查服务），替换点落在 `providers/` 的工厂（`specs/0001-email-forwarding-service/design.md` 已定，具体夹具实现见该特性 `plan.md` §7.2）。
- 替身必须与真实契约一致：**同一个 interface 的契约测试，真实现与替身都要过**。
- **禁止替换本次要验证的那一层**——「把仓储层 mock 掉，于是 SQL 从没被执行过」是最典型的假集成测试。

### 4.3 数据与隔离

- 每个用例自建数据，**不依赖预置种子数据**；结束清理或回滚。
- 必须可并行、可乱序、可重复；禁止「先跑 A 再跑 B」的隐式依赖；禁止断言全表计数这类会被其他用例污染的东西。
- 清表只清测试库；连接串通过环境变量覆盖，**不改仓库里的配置文件**。前置步骤与夹具落点见 `tests/integration/README.md` 与 `specs/0001-email-forwarding-service/plan.md` §7.2。

### 4.4 必测场景（跨特性类别）

这几类是本服务**最容易出错、且 mock 永远验不出来**的地方，每个新特性都要对照检查：

1. **幂等**：同一条记录被同一条流重复处理，结果不变、不产生重复副作用。
2. **并发抢占**：并发执行体抢同一批时，一条待处理记录只能被一个执行体拿到。
3. **重试与退避**：失败后的推进、上限、终态失败与最后一次错误被记录下来。
4. **状态迁移合法性**：声明的迁移能走通，非法迁移必须被拒绝。
5. **入站分拣与关联**：回复关联、退信识别、回执剔除、关联不上时的丢弃路径。
6. **外部能力契约**：`From` / `Reply-To` 这类身份与回路的硬约束（`AGENTS.md` §8）。
7. **保留期清理**：到期移除与其级联效果。

> 各条的**取值与判定依据**以 `docs/research/02-runtime-and-scheduling.md`、`docs/research/04-security-and-review.md` 与该特性 `design.md` 为唯一出处，本文件只规定「必须有测试覆盖」。

### 4.5 断言落点

断言**可观察结果**：响应体与状态码、数据库中的最终状态、外部系统实际收到的报文、发出的下一跳请求。

**日志面的两分口径**（`NFR-10` 与 `AC-13` / `AC-24` / `AC-28` 要求以日志留痕，所以日志不能一律禁断言）：

- **允许**：断言**结构化日志的事件名与受控字段**（例：`inbound_discarded` 事件的十一类计数与总数），以及「日志中不出现邮件正文 / 收件人地址 / 凭据」这类**否定断言**。断言的对象是事件名与字段，不是日志文案。
- **禁止**：用日志的**措辞**代替业务结果断言——业务状态与副作用必须由响应、库内终态或对端实收报文判定；也禁止断言私有内部状态、与业务契约无关的内部调用序列。

> 判据：把日志文案改写成另一句、事件名与字段不变——断言仍应绿；把业务结果改错——断言必须红。

**SQL 断言的口径**（判据同 R2，看的是**期望值从哪来**，不是「断言对象是不是文本」；`AC-26` 的抢占硬约束**只能**这么测——它要求从语句的编译产物证明 `FOR UPDATE` 与 `SKIP LOCKED` 同时存在）：

- **禁止**：把**手抄的整段 SQL 文本**当期望值——那是把实现复制进测试（R2），语句一改测试跟着改，换个等价写法还会误报。
- **允许**：断言语句**编译产物**的**结构性片段**——关键字（`FOR UPDATE SKIP LOCKED` 这类）、列名、参数绑定值、子句存在性（`ORDER BY` / `LIMIT` / `ON CONFLICT`）；片段内的期望值仍须由规格文本或模型对象的列定义推出（引用**结构真源**，不是用被测逻辑算期望值——被验的是语句结构与绑定），不得把编译输出直接抄进断言。

> 判据：改掉被断言的**结构**（去掉 `FOR UPDATE`、换排序或绑定列）→ 断言必须红；只换措辞 / 格式而结构不变 → 断言不应误报。整段文本的等值比对两头都做不到，所以它被禁。

### 4.6 分层与端到端节流

端到端只覆盖少量关键旅程，**不用端到端覆盖分支逻辑**——分支逻辑属于单测，协作正确性属于集成测试。测试金字塔不倒置：为一条分支逻辑写一个跨进程用例，是最常见的「测试很多、信心很少」来源。

### 4.7 失败可诊断与安全红线

失败输出要带请求 ID、关键输入摘要、SQL / 响应摘要，便于定位；但**不得打印邮件正文、附件、真实收件人地址、账号口令、原始 MIME**——排查用邮件 ID 引用（`AGENTS.md` §8）。夹具与期望值一律用 `example.com` 这类占位地址。

### 4.8 稳定性

任何不稳定用例**先隔离再修**，不允许靠重试、加 `sleep`、放宽断言转绿。**自动重试后才通过的用例视为失败。**

## 5. AI 写测试的作业流程（强制）

| 阶段 | 做什么 | 通过条件 |
|---|---|---|
| **0 输入** | 先取需求 / `AC-n` / 接口契约 / 不变量 / 失败语义。缺失就**停下来问**，**禁止从代码反推期望值** | 有明确的规格来源 |
| **1 行为清单** | 先只输出**要验证的行为清单**：业务规则、状态迁移、边界表、失败路径、不变量，逐条标注来源与优先级；另列「规格没写清楚 / 我读不懂」的疑点 | 人工确认清单后才动手写测试 |
| **2 先红后绿** | 优先 TDD。若确实是后补：先按规格写断言再运行；**与实现不一致一律作为发现上报，不许改断言去迁就实现** | 出现过一次红灯 |
| **3 隔离上下文** | 写实现的会话与写断言的会话**分开**；验收性质的用例放在写实现的一方改不到的位置 | 断言不是实现者对自己产出的自我确认 |
| **4 反向验证** | 故意破坏实现（改判定方向、改边界、改返回值、删分支）并给出「它红了」的输出证据，然后恢复；同时列出仍然存活的变异与未覆盖项 | 每条新增测试都有失败证据（R3） |
| **5 报告** | 交付：行为覆盖清单（含**未覆盖项**）、边界表、失败证据、不确定项，以及「哪些断言的期望值其实依赖了实现」的自我披露 | 未验证项被明示，不藏着 |

### 阶段 5 之后的禁令

禁止：改期望值、改断言、删断言、删测试文件、加 `skip` / `xfail`、把被测代码的返回值直接当期望、硬编码特定输入让测试通过、篡改评分或测试基础设施、改测试运行配置以隐藏失败、把本来正确的实现削弱来迁就测试。
**唯一出路**：测试失败 → 判定是实现错还是测试错 → 说明理由 → 交人工裁决。

> 为什么这条禁令要写死在规范里：当「测试通过」成为目标时，把测试改成通过会比修实现更省力，而**外部完全看不出区别**——绿灯看起来是一样的（实测数据见 `docs/research/03-dependencies-and-toolchain.md` 引用的变异测试基线）。

## 6. 门禁与完成定义

门禁五步的命令、顺序与失败行为见 `scripts/README.md`；**第 4、5 步的判据**（覆盖率为什么不是门槛、变异测试的三条结构性红线）见 `docs/research/03-dependencies-and-toolchain.md`。

一个测试变更**可被接受**的全部条件：

1. **可追溯**：每个 `AC-n` 都能找到对应测试（映射表在**该特性的** `plan.md`），没有说不清用途的孤儿测试；
2. **能失败**：新增行为都有失败证据（R3）；
3. **无空洞**：R5 清单零命中，无新增 `skip` / `xfail`，无「重新生成快照」式改写；
4. **无新增不稳定用例**：§4.8；
5. **体量合理**：新增测试数量与新增业务规则量级匹配，测试总时长不失控；
6. **红线**：第 5 步未触发任何一条结构性红线；**存活变异逐条评审**（区分「真漏测」与「等价变异」），评审结论写进 PR —— **门禁不设变异分数阈值**，判断由人做；
7. **未跑真实数据库的集成用例不计入通过**：容器未起时用例会被跳过，而**跳过不是通过**；涉及数据库语义的 `AC-n` 必须在起了容器之后才算验收。

## 7. 评审检查表

对照逐条问，答不上来就退回：

- **反向检查**：把这条断言对应的实现改成相反行为，它会红吗？→ 不会，直接打回。
- 这条期望值是从哪来的？（规格？手算？参考实现？）→ 回答「跑一遍看结果」即打回。
- 有没有 mock 掉被测对象自己或它的内部协作者？
- 有没有断言「某个方法被调用过」而不是「业务结果是什么」？
- 日志相关的断言落在**结构化事件名与受控字段**上，还是在赌某句日志文案？（§4.5 的两分口径）
- 边界两侧都测了吗，还是只测了远离边界的代表值？
- 能单独跑、乱序跑、并行跑吗？里面有 `sleep` / 真实时间 / 未播种随机 / 全局状态吗？
- 这次测试 diff 是**新增**还是**弱化**（改期望值、删断言、加 `skip`、重新生成夹具）？
- 失败的用例最后是「改实现」还是「改测试」修的？改测试的理由写清楚了吗？
- 测试数与业务规则数匹配吗，还是明显在灌水？
- 有没有哪条行为被测试「追认」为正确，但其实没人按需求验证过？
- **设计契约里被点名「必须同时成立 / 不得删除」的配置行还在吗？** 对照 `design.md` 等设计契约，逐条回到代码确认该配置行仍在、且与契约一致（R13）。这类行**可能没有自动检查兜底**——**门禁全绿不代表它们还在**。→ 答「门禁绿了」即打回。

## 8. pytest 标记约定

- **集成测试用例必须打 `@pytest.mark.integration`**；标记已登记在 `pyproject.toml` 的 `[tool.pytest.ini_options] markers`——未登记的标记会报 `PytestUnknownMarkWarning`。
- **容器未起时按标记跳过**：跳过判据（能否连上 PostgreSQL / 邮件服务）落在 `tests/integration/conftest.py` 的收集钩子里，随该夹具一起落地（`specs/0001-email-forwarding-service/plan.md` §7.2）。跳过的输出必须写明**为什么跳过**（哪一项依赖不可达），不允许静默跳过。
- **门禁刻意不启动容器**：`scripts/check.sh` 不加「先起容器」的逻辑，为的是让门禁依赖尽量少、随手就能跑。因此容器未起时第 4 步会跳过集成用例——**跳过不等于通过**（§6 第 7 条）。
- 想要完整的本地验收：先 `bash scripts/dev-up.sh` 起容器，再跑 `bash scripts/check.sh`。
- 单测**不得**依赖 Docker、容器与网络；`tests/unit/` 在容器未起时也必须全绿。

## 9. 提示词骨架

**A. 单测（先清单、后代码）**

```
为 <模块> 补单元测试，目标不是覆盖率，而是可证伪的业务验证。
输入：<AC-n 原文> + <公共接口签名>；先不要读实现。
先只输出：1) 业务规则清单（逐条标 AC 编号）2) 边界表 3) 失败路径清单 4) 你无法从规格确定的疑点。
我确认清单后再写测试，且必须：期望值来自规格或人工推导，不得调用被测代码生成期望；
断言具体值或具体异常类型 + 错误码；禁止断言替身被调用；禁止 assert is not None / 只断言没抛异常。
写完自报：哪些断言的期望值你不确定。
```

**B. 集成测试**

```
为 <跨层场景> 写集成测试，使用真实 PostgreSQL 与邮件服务（docker compose -f compose.dev.yaml），
只允许在 <外部第三方> 边界用替身，替换点在 providers/<...>/factory。
要求：每个用例自建唯一数据、可独立并行乱序运行、结束清理；断言落点为可见结果
（响应、库内终态、对端实收报文），不得断言日志文案或手抄的整段 SQL 文本
（允许断言结构化事件名与受控字段、以及语句编译产物的结构性片段，见 §4.5）；
必测：主流程、事务回滚、并发抢占互斥、幂等重放、重试与退避、外部依赖失败与半成功。
打上 @pytest.mark.integration。禁止因为「跑不通」而把真实依赖换成 mock——跑不通要报告。
```

**C. 反向验证（证明测试能失败）**

```
对每条新增测试，指出被测实现中对应的最小代码变更（改判定方向 / 边界 / 返回值 / 删除分支），
实际执行该变更并给出「测试失败」的输出证据，然后恢复代码。
最后列出仍然存活的变异、未被任何测试覆盖的分支，以及你认为无法验证的部分。
```

**D. 评审 AI 写的测试**

```
按 docs/testing.md §7 的检查表逐条审查这些测试：期望值来源、是否同义反复、是否 mock 了被测物、
是否有空洞断言、边界两侧、确定性与隔离、测试 diff 是新增还是弱化、是否在为绿而绿。
对每条给出：问题、文件:行、必须的修复动作。无法判断期望值是否正确的，标为「需人工确认」。
```

## 10. 已否决方向

- **把覆盖率设成验收门槛** —— 覆盖率衡量执行、不衡量验证；它会鼓励写「执行到但没断言」的测试。
- **把测试数量或断言数量当指标** —— 数量可被无成本地灌水，且会直接换来更慢的门禁与更重的评审负担。
- **用 mock 验证并发抢占或事务** —— 抢占用的是数据库语义，替身验证不了（既有结论的重申）。
- **让被测代码生成期望值**（含「先跑一次把输出粘进断言」）—— 这就是同义反复测试的成因，恒绿的断言比没有测试更危险：它会让人以为这块被覆盖了。
- **以「快照 / 重新生成夹具」的方式修失败用例** —— 那等于把期望值改成当前行为，等于放弃断言。
- **把项目代码当测试夹具的廉价替代**（在测试里复制一份业务逻辑来算期望值）—— 实现改错时两份会一起错。
