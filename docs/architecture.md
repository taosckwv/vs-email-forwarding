# 代码分层与依赖方向

> 本文件是**代码分层与依赖方向的唯一出处**：层怎么切、哪一层能调哪一层、两条触发路径各走哪一层、进程里跑着什么。
> 每层**放什么 / 不放什么**见 `AGENTS.md` §4 的目录职责表；数据模型、流水线细节、集成契约与依赖选型的结论见 `specs/0001-email-forwarding-service/design.md` 与 `docs/research/` 各册，本文件不复述它们，只给指针。
> 写作规范见 `docs/README.md` §4。

---

## 1. 分层总览

```text
                       调用方（内网 agent 会话）
                                │ HTTP
          ┌─────────────────────▼──────────────────────┐
          │ api/          HTTP 接口层                   │  唯一对外入口
          │  请求校验、响应序列化、依赖注入               │  不碰仓储、不直连 SMTP/IMAP
          └─────────────────────┬──────────────────────┘
                                │ 同步请求
          ┌─────────────────────▼──────────────────────┐
          │ service/      用例层：同步路径的业务编排      │
          └───────┬─────────────┬──────────────┬────────┘
                  │             │              │
        ┌─────────▼──┐   ┌──────▼───────┐  ┌───▼──────────┐
        │ core/      │   │ db/          │  │ providers/   │
        │ 纯逻辑      │   │ ORM / 引擎 /  │  │ smtp/ imap/  │
        │ 无 I/O      │   │ 会话 / 仓储层 │  │ review/      │
        │            │   │ (所有 SQL)    │  │ base.py 定接口│
        └─────────▲──┘   └──────▲───────┘  └───▲──────────┘
                  │             │              │
          ┌───────┴─────────────┴──────────────┴────────┐
          │ flows/        定时任务层：入口 + 编排         │  五条后台任务
          └─────────────────────────────────────────────┘

        schemas/   Pydantic 请求 / 响应模型（只被 api/ 用）
        config.py  唯一配置入口（pydantic-settings）+ 启动即校验
        constants.py  服务固定语义常量（状态取值、重试算术、受控枚举）；共享叶子层，谁都能 import 它
        main.py    FastAPI 组装：挂路由、随 lifespan 启停定时任务
```

**两层编排并列**：同步请求由 `service/` 编排，定时任务由 `flows/` 编排；两者互不调用，共用的纯逻辑在 `core/`，共用的落库在 `db/` 仓储层，共用的外部能力在 `providers/`。

## 2. 依赖方向

| 层 | 允许依赖 | 不得依赖 |
|---|---|---|
| `api/` | `schemas/`、`service/` | `flows/`、SQL 与仓储、`providers/` 的具体实现 |
| `service/` | `core/`、`db/`（仓储）、`providers/`（按需） | `api/`、`flows/` |
| `flows/` | `core/`、`db/`（仓储）、`providers/` | `api/`、`service/` |
| `providers/` | 各自 `base.py` 定义的接口 | `db/`、`core/`、`flows/`、`service/`、`api/` |
| `db/` | 无——只依赖 ORM 与会话本身 | 任何业务层：`core/`、`providers/`、`flows/`、`service/`、`api/` |
| `core/` | 无——纯逻辑 | 项目内任何模块、I/O 与数据库 |
| `constants.py` | 无——**共享叶子层**，只放常量 | 项目内任何模块（含 `config.py`）、I/O 与判定逻辑 |
| `schemas/` | 无 | ORM 模型 |

四条硬规则：

- **单向**：依赖只能自上而下（`api/` → `service/` → `db/` / `providers/` / `core/`），不得反向、不得成环。
- **跨边界只经接口**：外部能力一律走 `providers/` 各自的 `base.py`，业务流程不得 import 具体实现库；落库一律走 `db/` 的仓储层，业务流程不得裸写 SQL。
- **纯逻辑不许下沉 I/O**：`core/` 不得引入 I/O 与数据库访问，它必须能被单测直接调用。
- **共享叶子层是唯一例外**：`constants.py` 只放服务固定语义的常量，**不 import 任何项目内模块、不做 I/O、不含判定逻辑**，因此**各层（含依赖为「无」的 `db/`）都可以 import 它**。它的边界判据是「改了它等于改产品行为」——随环境变化的值属 `config.py`（`AGENTS.md` §7）。

## 3. 两条触发路径

**同步（HTTP 请求）**：`api/` 解析并校验请求 → `service/` 的用例编排（事务边界、调仓储、按需调适配器）→ 结果由 `api/` 序列化为响应。

**异步（定时任务）**：`flows/` 的每条循环在自己的 tick 内编排，统一走三阶段——认领（短事务）→ 调用（事务外）→ 落库（第二个事务）；**数据库事务不得跨越网络调用**。事务边界、认领条件与结果的细节见 `specs/0001-email-forwarding-service/design.md` 的「流水线」一节，本文件不复述。

两条路径都只经 `db/` 仓储层读写、只经 `providers/` 触达外部。

## 4. 运行时形态

- **单进程**：FastAPI 应用与全部后台任务在同一个进程里，后台任务随 `lifespan` 启停（`docs/research/02-runtime-and-scheduling.md`）。
- **五条后台任务**：流① 审查出站、流② 发信、流③ 拉取入站、流④ 审查回复，外加保留期清理；各自独立循环、独立间隔、独立分批。调度器与这五条循环都落在 `flows/`。
- **两套模型**：`db/` 管 ORM 模型，`schemas/` 管 Pydantic 请求 / 响应模型，两者不混用（`AGENTS.md` §4）。
- **配置与启动**：`config.py` 是唯一配置入口，并在启动时完成校验（`specs/0001-email-forwarding-service/design.md` 的「启动即校验」）。

## 5. 数据库引擎与会话的生命周期

**引擎是进程级单例，会话按阶段开、随阶段关。**

- **引擎单例**：`db/` 在 FastAPI 的 lifespan 里按配置层的 `DATABASE_URL` 创建一个异步引擎，进程内共用这一个实例，lifespan 退出时统一 `dispose()`；连接池用 SQLAlchemy 的默认口径，不另设数值——五条后台任务每 10 秒一批、每批不超过 `BATCH_SIZE` 条，池子不是瓶颈。
- **短会话**：`api/`、`service/`、`flows/` 都不持有常驻会话。同步请求路径每次调用由 `db/` 的会话工厂开一个短会话；后台任务在 tick 的每个阶段各开一个短会话，用完即关。
- **会话不跨网络调用**：一次 tick 的三阶段——**认领（短事务）→ 调用（事务外）→ 落库（第二个事务）**——各用独立的短会话，认领事务在调用外部能力之前已提交。这是 §3 那条「数据库事务不得跨越网络调用」在会话生命周期上的落法，同一件事的细节（认领条件与结果）在 `specs/0001-email-forwarding-service/design.md` 的「流水线」一节。
- **会话不跨任务共享**：五条后台任务各开自己的会话，任一实时会话都不在任务之间传递。
- **仓储层只接收会话**：仓储函数由调用方传入会话，自己不开引擎、不管事务边界；事务边界属于 `service/` 与 `flows/` 的编排。`db/` 的会话与 ORM 类型只作 `db/` 的内部契约，不作为 `api/` 的函数参数或返回值类型。

### 已否决方向

- **每条后台任务持一个常驻会话（存活整个进程）** —— 会话常驻会把事务边界拉长到跨网络调用，长事务期间连接被长期占用，会话失效还要额外处理重连。按阶段开短会话使「事务不跨网络调用」成为结构上的自然结果，而不是靠每次记得提交。
- **引擎按请求或按任务创建** —— 每个引擎自带一个连接池：按请求建会不断重建池，按任务建会让五条任务各持一批连接。两者都让连接总数不受控，也让 lifespan 的创建与释放失去单一落点。
