## 一句话定位

`vs-email-forwarding` 是一个**内部邮件中转服务**：DSH 会话不直接发信，而是把要发送的内容通过 HTTP API 交给本服务，由本服务负责安全审查、投递，以及回收并审查回复。调用方是内网 DSH 会话，要解决的是「外发邮件由服务端统一审查与投递，且对方回复能被收回并同样过审」。项目**当前处于预研阶段**，业务逻辑尚未实现。

依据 `AGENTS.md` §1（项目是什么）与 §2（当前阶段）。主流程**原样引自 `AGENTS.md` §1，未改写**：

```text
DSH 会话
  │  POST /v1/messages
  ▼
待审表 (pending)
  │  流① 审查出站：敏感信息 / 病毒审查
  ├─ 通过 ──→ 邮件表 (queued)
  └─ 不通过 → 拒审表 (rejected)
                  │
                  │  流② 发信：查出未发送记录 → SMTP 投递
                  ▼
             （外部收件人）
                  │  回复
                  ▼
              专用回复邮箱
                  │  流③ 拉取入站：IMAP 拉取回复
                  ▼
              待审表 (inbound)
                  │  流④ 审查回复：同样的安全审查
                  ├─ 通过 ──→ 邮件表 (received)
                  └─ 不通过 → 拒审表
                                │
                                │  GET /v1/messages/{id}/replies
                                ▼
                            DSH 会话取回回复
```

## 已冻结的决策一览

每条只写结论；**理由与被否决的备选方案一律留在对应 ADR**，本文档不复述。

- 技术栈：Python 3.13 + `uv`（管解释器、虚拟环境与锁文件）+ FastAPI / uvicorn，配置 pydantic-settings，日志 structlog —— 见 ADR-0001
- 仓库形态：单包仓库 + `src` 布局（`src/vs_email_forwarding/`），发行名 `vs-email-forwarding`、导入包 `vs_email_forwarding` —— 见 ADR-0002
- 许可证与治理：MIT，私有仓库**完全按开源规范**治理（GitHub、暂不发布制品、手工 CHANGELOG + 语义化版本） —— 见 ADR-0003
- AI 协同模型：**规格驱动**；`AGENTS.md` 为唯一真源、按目录分层局部 `AGENTS.md`、PR 强制关联 spec 编号、`skills/` 固化固定流程 —— 见 ADR-0004
- 部署形态：生产目标 CentOS 8（系统保持不变）；应用与 PostgreSQL 都以 Docker 容器跑在同一台机器上，数据卷挂载宿主机目录；交付物为镜像 tar + 运行脚本 —— 见 ADR-0005
- 基础镜像与预演：生产基础层锁 `python:3.13-slim-trixie`（锁 codename tag、不用 alpine 变体），预演容器用 `almalinux:8`（仅预演、不用于生产），同机 PostgreSQL 用 `postgres:17`；平台在构建期钉死 `linux/amd64`，`save` / `load` 不传 `--platform`，只交付单平台 amd64 归档并做交付前自检 —— 见 ADR-0006
- 调度方式：进程内 asyncio 后台任务，四条流并发、各自独立循环 / 开关 / 间隔，随 FastAPI lifespan 启停；默认间隔 10 秒，但间隔与每批条数一律是配置项 —— 见 ADR-0007
- 数据库与幂等抢占：PostgreSQL；开发、预演、生产全部容器化；单实例部署，但抢占一律用 `SELECT ... FOR UPDATE SKIP LOCKED` + 状态字段 + `next_attempt_at`，**禁止「先 SELECT 判断、再 UPDATE」**；开发库与测试库分离，测试用真实 PostgreSQL —— 见 ADR-0008
- 审查能力（一期）：安全审查实现为「永远通过」的空实现占位，接口先留好；拒审表与拒审链路仍建表预留 —— 见 ADR-0009
- CI：**不跑 CI**，`.github/` 下不建 `workflows/`；门禁落在 pre-commit + `scripts/check.*`；版本与 CHANGELOG 手工维护，不采用 `python-semantic-release` —— 见 ADR-0010
- 中文标点与 ruff：强制中文标点；在 `pyproject.toml` 显式 ignore `RUF001` / `RUF002` / `RUF003`（记录例外，不是为过门禁而放宽），其余规则与 mypy / pytest 标准不放宽 —— 见 ADR-0011
- 发件人身份与回复路由：`From` **固定取服务配置** `MAIL_FROM_ADDRESS`、**不允许调用方指定**；服务端**显式写入 `Reply-To`**，其值等于 IMAP 拉取所用的信箱 `REPLY_TO_ADDRESS` —— 见 ADR-0012
- 交付形态变更：镜像**在 CentOS 8 生产服务器上本地构建**（不再由开发机构建），**基础镜像以 tar 带入**并 `docker load`；环境前提更正为「**与公网隔离、可达内网镜像源；运行时不得依赖任何外部网络**」 —— 见 ADR-0013
- 项目定名：`vs-email-forwarding`（导入包 `vs_email_forwarding`），镜像名 / compose 项目名与容器名前缀 / env 前缀 / 数据库默认名同步派生 —— 见 ADR-0014

## 已确认的边界

依据 `AGENTS.md` §2 的「已知且已确认的边界」与「已定的关键行为」，一行一条：

- 不支持附件（一期明确不支持）—— 见 `AGENTS.md` §2
- 无 Web 管理后台，纯后台服务 —— 见 `AGENTS.md` §2
- API 鉴权先不做：服务仅内网可达，因而当前不需要鉴权；但**在 API 层预留鉴权位置**，后续接入不需要重排路由结构 —— 见 `AGENTS.md` §2
- 审查一期只做占位：**定义接口与输出**，**不做任何真实检测**（不查敏感信息、不引入病毒扫描引擎、不接外部审查 API）—— 见 `AGENTS.md` §2（决策见 ADR-0009）
- 发信走 **SMTP 直连**（企业邮箱 / 自建 MTA），参数全部来自 `.env` —— 见 `AGENTS.md` §2
- 收信走 **IMAP**：单专用回复邮箱 + **UID 游标增量拉取** + 用 `References` / `In-Reply-To` 关联原邮件 —— 见 `AGENTS.md` §2
- 关联不上的邮件标记为**孤儿**，但**仍然入库、不丢数据** —— 见 `AGENTS.md` §2
- 发信失败重试 **3 次**，退避 **15s / 30s / 60s**，之后进入终态失败 —— 见 `AGENTS.md` §2
- 生产 PostgreSQL 与应用**同机**，跑容器 + 宿主机数据卷 —— 见 `AGENTS.md` §2
- 发信的 `From` 只能来自服务配置、绝不允许调用方指定；服务端必须显式写入 `Reply-To`（等于 IMAP 拉取所用的信箱）—— 见 `AGENTS.md` §2 与 ADR-0012
