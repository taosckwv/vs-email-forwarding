# specs/ — 规格驱动开发约定

本目录存放**每个特性的需求、设计、实现计划与任务清单**。它是本仓库「先想清楚、再动手」的落地方式：AI 与人都在同一份规格上对齐，代码只是规格的实现结果。

规则源头是 `AGENTS.md` §5「规格驱动工作流（强制）」。本文件是它的展开说明。

---

## 1. 为什么要有 specs/

AI 协作最常见的失败模式**不是写不出代码，而是不知道边界在哪、验收标准是什么**。规格文件解决的就是这件事：

- `spec.md` 回答「**要什么、怎样算做完**」；
- `design.md` 回答「**本特性的设计结论是什么**」（数据模型、流水线细节、集成契约、依赖选型）——**它是该特性设计结论的唯一真源**；
- `plan.md` 回答「**怎么实现、会动哪些地方**」；
- `tasks.md` 回答「**现在做到哪一步**」。

四者在**实现阶段**缺一不可。只有 spec 没有 design，实现会各自发明数据模型；只有 design 没有 spec，做完也无法证明做对了。
但它们的**写作时点不同**：`spec.md` 先写并交所有者确认，`design.md`、`plan.md` 与 `tasks.md` 在确认**之后**才写（见 `AGENTS.md` §5 与下文 §3）。因此一个只有 `spec.md` 的目录在 `待确认` 阶段是正常的，不是残缺。

## 2. 目录与命名

```
specs/
├── README.md                       ← 本文件
├── _template/                      ← 模板：复制，不要改写模板本身
│   ├── spec.md
│   ├── design.md
│   ├── plan.md
│   └── tasks.md
├── 0001-outbound-review-pipeline/
│   ├── spec.md
│   ├── design.md
│   ├── plan.md
│   └── tasks.md
└── 0002-...
```

- 目录名格式：`NNNN-英文短横线-slug`，编号**四位递增**，从 `0001` 开始，不复用已删除的编号。
- **目录名与文件名一律 ASCII**，`spec.md` / `design.md` / `plan.md` / `tasks.md` 四个文件名固定不变。
- **文件内容用中文。**
- 一个目录 = 一个特性。**不要**把不相关的改动塞进同一个 spec。

创建方式：复制模板目录，然后重命名。

```powershell
# Windows
Copy-Item -Recurse specs/_template specs/0001-outbound-review-pipeline
```

```bash
# Linux / CentOS 8
cp -r specs/_template specs/0001-outbound-review-pipeline
```

## 3. 状态流转

每份 `spec.md` 的元信息表里必须有一个**状态**字段，只允许取以下值：

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `草稿` | 正在写，随时会改 | 继续补充内容 |
| `待确认` | 已写完，等所有者确认 | 补写内容；**不得写 `design.md` / `plan.md` / `tasks.md`，不得写实现代码** |
| `已确认` | 所有者确认，可以动工 | 写 `design.md`、`plan.md` 与 `tasks.md` |
| `实现中` | 正在实现 | 勾选任务、更新进度 |
| `已完成` | 全部 `AC-n` 通过 | 回填验收结果，保留 spec |
| `已废弃` | 被其他 spec 取代 | 在文件顶部写明取代者编号与原因 |

**从 `待确认` 到 `已确认` 只能由所有者推动。** AI 不得自行把状态改成 `已确认`，也不得在状态不是 `已确认` / `实现中` 时修改 `src/` 下的实现代码。

**`design.md`、`plan.md` 与 `tasks.md` 在 `已确认` 之后才写**：确认过程会改 spec，设计与计划依附于 spec，先写必然返工（见 `AGENTS.md` §5）。因此 `待确认` 阶段的 spec 目录里只有 `spec.md` 是正常状态。

**元信息表不写日期**：进度只看状态字段；时间线一律不记录（见 `docs/README.md` §4）。

## 4. 验收标准必须可测试

这是本目录**最硬的一条要求**。

- 每条验收标准编号 `AC-n`，且必须能被**一条命令、一个自动化测试、或一组明确步骤**判定真假。
- 每条 `AC-n` 必须能追溯到至少一条功能需求 `FR-n`；`FR-n` 必须至少被一条 `AC-n` 覆盖。**没有被任何 AC 覆盖的 FR 不允许进入 `已确认`。**
- 禁止的写法（不可测试）：
  - 「功能运行正常」
  - 「性能良好」
  - 「错误处理完善」
  - 「用户体验友好」
- 合格的写法：
  - 「同一封邮件在 10 秒内被两条流同时抢占时，SMTP 投递**恰好发生一次**；可由集成测试 `test_no_duplicate_send` 验证。」
  - 「`POST /v1/messages` 在缺少 `to` 字段时返回 HTTP 422，响应体包含字段名 `to`。」
  - 「拒审邮件不出现在邮件表中；`GET /v1/messages/{id}` 对该 id 返回 `status=rejected`。」
  - 「在与公网隔离、可达内网镜像源的服务器上启动容器（运行时不得依赖任何外部网络），60 秒内 `/healthz` 返回 200。」

> 写不出可测试的验收标准，通常意味着**需求本身还没想清楚**——这时应该回到 `未决问题` 一节，而不是把模糊表述写进 `AC`。

## 5. 与其他目录的分工

| 问题 | 去哪找 |
|---|---|
| 这个特性要什么、怎样算做完 | `specs/<编号>/spec.md` |
| 这个特性定下了什么设计结论 | `specs/<编号>/design.md`（该特性设计结论的唯一真源） |
| 怎么实现、动哪些文件 | `specs/<编号>/plan.md` |
| 现在做到哪一步 | `specs/<编号>/tasks.md` |
| 跨特性底座的当前结论（为什么这么选） | `docs/research/` 下对应的主题册 |
| 系统级架构与数据模型说明 | `docs/` |
| 尚未定案的问题 | `docs/open-questions.md` |
| 固定流程怎么走（可复用） | `skills/` |

**不要把需求写进 `docs/`，也不要把跨特性底座写进 `specs/`。** 某特性的设计结论属于该特性的 `design.md`，跨特性底座属于 `docs/research/`；三者的读者与生命周期不同。

## 6. AI 协作要求

1. **AI 先写 `spec.md`，等确认，再动代码。** 不允许「先写代码再补规格」。
2. AI 写 `spec.md` 时，如果发现某处**必须现在决策但对话中没有定案**，必须停下来问所有者，并把该问题登记到 `未决问题` 一节；**不要自行选择一个看起来合理的默认值**。
3. AI 实现时，每完成一条 `tasks.md` 中的任务，必须：
   - 勾选该任务；
   - 标注它对应的 `FR-n` / `AC-n`；
   - 若发现任务描述与 `spec.md` 冲突，**先改 spec 并重新确认**，不要默默按代码走。
4. AI 实现完成后，必须逐条报告 `AC-n` 的验证方式与结果，写回 `spec.md` 的「验收结果」一节。
5. 若实现过程中发现某个 `AC-n` 无法被测试，那就是 spec 的缺陷——**回到 spec 修它**，不要跳过。

---

## 7. 完成后不要删

特性实现并验收完成后，`specs/<编号>/` **保留在仓库里**。它是这个特性的历史依据：用来回答「当初为什么这么做」「这个行为是什么时候引入的」。删除 spec 等于丢失决策上下文。

只有被明确取代时，才把状态改为 `已废弃` 并在顶部注明取代者。
