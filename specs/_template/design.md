# 设计文档（<特性名> · `specs/<NNNN>`）

> 本文件是 `specs/_template/design.md` 模板的实例。**填写说明用引用块标出，写完请删除所有引用块。**
> 本文件是该特性设计结论的唯一真源：数据模型、流水线细节、集成契约与依赖选型的结论都在这里。
> 需求在 `spec.md`；跨特性底座（调度载体与并发抢占硬约束、技术栈与门禁、安全红线、交付与环境、命名与治理）在 `docs/research/` 各册，本文件只在需要时给指针，不复述。
> 写作规范见 `docs/README.md` §4：只写当前有效内容，不写时间线与决策过程。

## 1. 概览

> 用一段话说明这个特性做什么（只讲做什么、给谁用，不讲实现细节）；放一张总览图，并说明这张图以什么为准；再用一张短表集中列出本设计的不变量，每条只给结论、理由指回后面对应的小节。
> 图里只画参与数据流转的主流程；不参与数据行流转的后台任务（如清理）在正文用一句话说明即可，不入图；同一张物理表若在图中出现多次，注明实际是同一张表。
> 不写日期、时间线与决策过程。

## 2. 数据模型

> 先一句总述（本特性共有几张表、各是什么）；再用 Markdown 表逐张列出字段，列为「字段 / 类型或取值 / 说明」，类型写清楚（主键、文本、时间戳、整型、受控枚举的取值集合），未写明类型的不要臆造。
> 「说明」列不得留空：只写本文件已写明的语义，写不出来就显式标注「语义未写明」，不要猜。受控枚举除取值集合外，还要给每个取值写清含义与谁在用。同一个中文词若指多个不同对象，逐处用统一称谓区分，不要让读者跨节对照才知道是几样东西。
> 再用一张表列约束与索引（唯一索引、部分唯一索引、抢占索引、查询索引、清理索引、`CHECK`）；然后写状态取值与合法迁移（含为什么没有中间态、代价是什么）、时间字段表与排序键、内容字段与长度上限（上限是配置项还是代码常量）。

## 3. 流水线

> 先说明后台任务由哪几条流构成，调度载体属跨特性底座时只给指针；再说明统一的认领方式与事务边界（两阶段认领、事务不得跨越网络调用）及其代价。
> 每条流一小节，按「认领 → 调用 → 落库」的顺序写，并写明事务边界；理由与代价放进每节末尾的「为什么这么做」小段，不要揉进结论句里。
> 收尾写清理流与崩溃重启后的恢复，只写本特性相关的那部分。

## 4. 集成契约

> 本章标题固定为「集成契约」——仓库里有多处指针按这个名字引用它，不要改名。
> 写对外 API 的端点表、请求字段、响应字段与状态取值、错误与校验（如 422）规则、对外返回的时间格式；再写与外部系统 / 供应商接口之间的契约：输入与输出的受控枚举、异常语义、身份与路由、启动即校验、外部参数的来源。

## 5. 依赖选型

> 用一张表写每个依赖的「库 / 许可 / 用途 / 换来的好处 / 代价」。
> 「实测证据」小节写支撑上面结论的实测结果：版本、许可、类型标注的有无，以及这些事实的来源方式。**不写没验证过的值。**
> 依赖**清单**记在 `docs/research/03-dependencies-and-toolchain.md`，这里只写选型论证。

## 6. 已否决方向

> 按主题分组，每组一个小标题；每条压成一行「否决了什么 —— 关键理由」，保留代价与风险，去掉重复论证与历史标注。本节放文档后部，作为附录性质，不要打断正文阅读。
> 正文某节已展开论证的条目，这里只留「否决了什么 + 一句理由 + 详见 §X」，但**条目本身不删**——决策记录必须完整。
> 跨特性底座的否决方向属于 `docs/research/` 对应册，不写在这里。

## 7. 落地位置

> 每条「路径 —— 放什么」，精确到仓库相对路径，按目录分组或排序。

## 8. 未定项
